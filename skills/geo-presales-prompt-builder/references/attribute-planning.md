# Attribute × Topic 属性规划（v8）

## 目标

生成 Prompt 前，先从接口 Case 的原始业务字段派生买家会用于入围、比较和选型的决策关注点，再在每个 Topic 内划分 P1 / P2 / P3。这里的 Attribute 不是产品参数清单：它可以是产品能力、使用场景、患者或服务对象痛点、采购约束、供应风险、交付要求或适用边界。P1 / P2 / P3 是属性在当前 Topic 下的优先级，不是属性类型或 Prompt 优先级；同一能力或痛点可在一个 Topic 为 P1，在另一个 Topic 为 P2 或不适用。Topic 是纵向主组织，Attribute 是横向战略认知，两者不互相替代。

`attribute_plan` 是 Builder 从现有 Case 字段自动派生的中间产物，不是销售或 Case 新增的手工输入。不使用旧 `target_attributes`，不生成 Attribute ID。逐题通过 `Attribute: {attribute}` Tag 回指这里的人类可读 Attribute 名，不再创建逐题属性 ID 或单独的 `attributes` 字段。

## 来源与本地适配

Profound AEO Guide 提出“当前关联”和“目标属性”，并建议从重要性、当前认知差距、可改变性三个方面判断属性优先级。原始方法没有定义 P1 / P2 / P3，也没有“入围属性”“比较属性”“补充属性”等分类。

Profound 的属性类目同时覆盖品牌侧和买家侧，这一点与《售后生词规则》§3 的十二类骨架一致：品牌侧是品类、产品特性、差异化优势、集成、信任与合规；买家侧是垂直行业、买家角色／目标企业画像、痛点、使用场景、购买标准、地理与市场、限制与边界。**买家侧这几类本身就是属性，不需要先转写成“客户意图”再回头映射。** ICP、画像、痛点、场景是“品牌为谁、在什么情况下被选中”，对客确认表的「客户问题与场景」列是“买家在哪个场合发问”，两者是不同对象：属性决定优化哪项认知，意图决定在哪个问句里去争这项认知。

P1 / P2 / P3 是本项目为了安排首批监测问题覆盖而增加的属性优先级。生题时还没有监测回答，只能依据属性对客户决策的影响和 Case 证据是否充分来分级，不得虚构“当前认知差距”。采集后再结合真实差距和可改变性安排内容与运营动作，不属于本 Skill。

## 与 Topic 和 Tags 的边界

- 一个候选本身代表可长期独立监测的市场、Use Case、ICP 或战略机会，并能形成完整 Prompt 集合时，它应由上游作为 Topic，不再重复派生为同名 Attribute。
- 一个候选是能力、特征或评价标准，可在多个 Topic 中复用时，将它作为 Attribute；例如 `Night Vision` 可同时属于智能行车记录仪和家庭安防摄像头。
- 诊断意图、Branded / Non-Branded、购买阶段、地区等只是 Tags，不进入 `attribute_plan`。

## 候选属性抽取

只能从 `品类 / 目标企业画像 / 目标客户 n / 痛点 n / 使用场景 n / 产品特性 n / 差异化优势 / 适用边界 / 购买标准 / 集成与兼容 / 信任与合规 / 地理与市场 / 补充内容` 抽取。先合并同义和强重叠的陈述，再评估：

1. 是否对当前 Topic 的买家有意义。
2. 是否会改变供应商入围、对比、偏好或选型。
3. Case 原字段是否足以支持，英文转写是否会扩张成新事实。
4. 它是品类级能力，还是仅对单款 SKU 成立的精确值。

候选不必是产品特性。以下也可以成为有效 Attribute，只要能改变当前
Topic 下的买家决策：

- 具体使用场景，例如夜间、旅行、长期家庭治疗或外出移动。
- 患者、护理方或服务商痛点，例如噪音、重量、操作负担或流量适配。
- 采购和交付约束，例如认证文件、供货稳定性、交期、备件和售后。
- 适用边界，例如固定式与便携式组合、连续流与脉冲流的适配范围。

新增 Discovery 前必须同时满足：

1. **Case 有依据**：能回指至少一个当前 Case 字段，不能只来自模型常识或品牌自述的扩写。
2. **买家会问**：有明确角色、场景或采购痛点，问题像真实采购/配置问题，而不是内部能力盘点。
3. **独立决策**：答案会改变候选集合、比较维度、采购偏好或适用判断；只是同一问题的换说法不算新增。

三门未同时通过时，候选进入 `excluded`、待客户确认或研究待办，不生成 Discovery。

抽取完成后做两个覆盖自检（只报缺口，不补内容）：

1. **约束覆盖**：对照约束类型清单——预算/价格、买方规模、垂直行业、地理、语言、使用场景、集成兼容、信任合规、紧急程度、用户画像、明确偏好——检查 Case 证据支持的约束是否都进了属性或题面。清单是查漏维度不是配额；Case 没有证据的约束类型记入待客户确认或研究待办，不得凭常识补齐。
2. **结果导向表述**：买家常按"要达成什么结果"发问而不是按能力名发问。若某 P1/P2 属性的题面全部是能力式表述，检查 Case 的痛点/使用场景字段是否支持一条结果式问法；不支持就保持现状，不为换框架造新意图。

进入 `excluded` 的候选，它的名称也不得再作为任何题目的 `Attribute:` 标签出现：被排除意味着它不改变购买决策，那么以它命名的题同样不改变购买决策。**已经排除的能力不能换个说法留在标签里**，也不能为了给某道题一个"归属"而回指排除项——这道检查由 validator 确定性执行（Trip.Biz 实例：一道题挂在 `excluded` 的品类基本能力上，靠人工复核才发现）。

同一能力被多个独立 Case 字段共同支持时（例如同时出现在痛点、产品特性和差异化优势中），它的输入证据更充分，但不能仅凭字段数量升为 P1。优先级仍由它对当前 Topic 下客户决策的影响决定；`source_field` 只记录最能代表决策含义的那个字段。`差异化优势` 回答“品牌为什么赢”，`适用边界`回答“品牌不适合谁”，两者通常能提供有价值的分级依据，但不能自动成为 P1。

## 优先级含义

新分阶段产物只采用下表的决策含义，不采用数量配额或 Verification 用途。表中数量用于兼容未声明 `generation_stage` 的历史合同。

| 优先级 | 每 Topic 数量 | 决策含义 | 题型用途 |
|---|---:|---|---|
| P1 | 历史 3–5；新阶段无配额 | 当前 Topic 下优先级最高，决定是否进入候选集合，缺失时可能直接淘汰 | Discovery 覆盖已有 P1；Competitor 优先使用；默认不生成 Verification |
| P2 | 建议 5–10 | 当前 Topic 下优先级居中，明显影响横向比较、偏好和最终选择 | 主要进入 Discovery 和 Competitor，不进入首轮 Verification |
| P3 | 0–10 | 当前 Topic 下优先级较低，但仍有购买参考价值 | 只在题量有余量且 P1/P2 已充分覆盖时进入 Discovery |
| Excluded / Accuracy | 不计入属性数 | 不改变购买决策，或属于需要独立真值的精确事实 | 删除，或用 `accuracy_only` 保留给独立 Accuracy 合同 |

属性少不等于 Case 有误，只要足以支持独立购买意图；不从输入外补齐。不同 Topic 的属性和问题数量可以不同，不以平均分配或补齐数量判断完整度。P3 不是低价值事实的收容所；纯目录归类、公司名称、无决策意义文案进入 `excluded`。单款 SKU 的精确值进入 `accuracy_only`，有购买意义的能力可在不扩张原文的前提下抽取。

## 分阶段使用

新题库显式 `generation_stage=discovery` 或 `diagnostic`：属性数量由证据与问题决定，不设 P1/P2/P3 配额，三档都可为空。P1 仍必须由 Discovery 的 Attribute Tags 覆盖。`verification_statement` 不要求生成；继承旧规划时可保留非空原值，但不代表已核验事实。不要为了覆盖属性而另造买家意图。

上文分级表的数量和 Verification 用途仅用于读取省略 `generation_stage` 的历史 v8 / v7 合同，不是新题库门槛。属性规划由 Agent 从现有业务字段完成，不是客户要提交的完整属性库或旅程矩阵。

## v8 `attribute_plan` 合同

`config.attribute_plan` 对每个 Topic 恰好保留一项：

```json
{
  "topic_id": "topic_1",
  "priorities": {
    "P1": [
      {
        "attribute": "视觉规格选型",
        "source_field": "产品特性 1",
        "source_value": "Case 原字段完整值",
        "decision_reason": "像素间距、亮度和刷新率决定显示屏能否匹配场馆。",
        "verification_statement": "It supports LED display selection based on pixel pitch, brightness, refresh rate, color, and image quality."
      }
    ],
    "P2": [
      {
        "attribute": "项目总成本控制",
        "source_field": "痛点 1",
        "source_value": "Case 原字段完整值",
        "decision_reason": "会明显影响供应商比较和最终选择。"
      }
    ],
    "P3": []
  },
  "excluded": [
    {
      "candidate": "官网将 LED 显示屏列为独立产品类别",
      "source_field": "差异化优势",
      "source_value": "Case 原字段完整值",
      "reason": "仅说明官网信息架构，不改变入围或选型。",
      "route": "exclude"
    }
  ]
}
```

历史规划 P1 比 P2/P3 多一个 `verification_statement`，新分阶段产物可省略。当前 Topic 的 `validation_items` 与 Verification Attribute Tags 对 P1 的强绑定已随 Verification 配额归 0 暂停使用；Verification 不在默认售前题库中，只有另行确认的验证合同才使用。

## 题型分配检查

- Verification：默认配额 0，不生成题；P1 的属性级正确性核查并入 Accuracy 合同。
- Discovery：每个 P1 至少有一道问题测试并写入对应 Attribute Tag；其余单属性题优先覆盖 P2；P3 仅在仍有明确独立决策价值且总量有余量时进入。某个 Topic 已覆盖全部重要决策关注点后立即停止，不因其他 Topic 的题量而补齐。
- Competitor：使用双方都能合理比较的 P1 和高优先 P2；同 Topic 多个竞品保持维度、题面和 Attribute Tags 同构。
- Category Awareness：询问品类和评价方法，语义上优先回到 P1 选型标准，不在题面罗列属性。
- Evaluation：新阶段按需选目标品牌或适用竞品；历史未声明阶段的题库才逐品牌覆盖。只使用 Topic 具体业务范围，不把属性列表塞入固定模板。
