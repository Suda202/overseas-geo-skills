# 售前与售后共用：监测问题生成原则

## 适用范围

售前和售后的题量、固定题型与数据来源可以不同，但生成监测问题时共用同一条主线：

`业务边界与信号收集（Customer / Market Signals）→ 提炼属性矩阵 → 候选主题 → 买家关注点与优先级 → 发现型问题 → 标签与质检 → 客户校正与锁词`

**先收集信号，再提炼属性。** 销售与 CRM 语言、客服与成交流失记录、评论与社区语言、GSC/SEO 查询、已采集的 AI 回答都属于信号层，是调研阶段要收的东西；属性矩阵是它们的提炼结果，不是起点。不要先填一张属性表、再去找信号印证它。信源的权重随买家类型变：B2B 以一手材料为主，消费品牌反过来，公开材料往往就能撑住分析。

- 主题（Topic）说明长期监测哪个市场、场景或业务机会。
- 属性（Attribute）是买家决策关注点：希望 AI 在哪个维度认识品牌。它不限于产品能力，也可以是买家侧维度（垂直行业、目标企业画像／买家角色、痛点、使用场景）或采购侧维度（购买标准、集成与兼容、地理与市场、限制与边界、信任与合规）。
- 客户问题与场景不是属性的一类，而是需求侧的另一对象：买家在哪个场合发问。属性决定优化哪项认知，意图决定在哪个问句里争这项认知。两者都要保留、各走一遍，既不合并成一列，也不把属性缩成品牌能力清单。对客确认表的这一列叫「客户问题与场景」（2026-09-22 由「客户意图」改名），内容仍按需求侧对象理解。
- P1、P2、P3 是属性在某个主题下的优先级，不是属性类型，也不是问题类型。同一属性在不同主题下可以有不同优先级。
- 标签（Tags）记录问题用途、品牌范围、属性及其他横向分类，不代替主题或属性。
- **Prompt Task 与 Intent 分开**：Prompt Task 描述买家正在完成的任务，Intent 描述后端分析用途。Task 可以扩展，不能自动改变 `analysis_type`、`formal_visibility_eligible` 或正式指标口径。

研究时可先发现买家关注点，再形成 Topic；Case 保存业务事实与选题依据，Prompt Builder 再派生轻量属性规划，不要求客户另填完整属性库或旅程矩阵。Journey 与诊断 Intent 分开，确有来源时用现有标签表达。

## 与 Profound 方法的关系

Profound AEO Guide 提出了“当前关联”和“目标属性”，并建议从重要性、当前认知差距、可改变性三个方面判断属性优先级。原始方法没有定义 P1、P2、P3，也没有“入围属性”“比较属性”“补充属性”等分类。

P1、P2、P3 是本项目为生成和覆盖监测问题增加的属性优先级：

- P1：当前主题下优先级最高，必须被问题覆盖。
- P2：优先级居中，在能形成独立购买问题时覆盖。
- P3：优先级较低，只在仍有新增诊断价值时覆盖。

生成首批问题时还没有监测回答，不能虚构“当前认知差距”。此时只根据客户决策影响和输入证据是否充分来划分 P1、P2、P3。采集后再结合真实认知差距和可改变性安排内容与运营动作，这属于售后分析，不反向伪造首批问题的依据。

## 共用的生成原则

1. 只使用当前阶段真实可用的输入和证据，不补造人群、场景、地区、规模或产品事实。
2. 每道问题只承担一个主要任务，单独拿出来也能理解和回答。
3. 问题要像真实用户会问的话，明确要求候选、判断、比较或评价结果，避免只问空泛定义。
4. 不在题面预设品牌优势、期望结论或胜负关系。
5. 品牌范围以题面实际出现的品牌为准，不能只靠标签声明。
6. 竞品比较采用一对一问题。同组比较尽量只替换竞品名称，保持场景、条件和比较维度一致。
7. 缩写、同名品类和跨行业歧义必须在题面内消除，不能指望下一轮追问澄清。
8. 不按字段数量机械生题。**去重的单位是购买决策，不是措辞**：两题指向同一购买决策（同一候选集合、同一比较维度、同一改变答案的条件）就只保留一题；只有买家、地区、场景或决策阶段变化才算新题。
9. 只换措辞、不增加诊断价值的问题不算新问题，不能用来凑题量。
10. **宽 Topic 要落到切面**：一个 Topic 下能识别出多个彼此不同的买家需求时，逐条标出所属切面，把配题重心放在品牌优势与买家需求重合的切面上，不平均分配；不要用「一个宽标签下面每题讲一个不同需求」撑开题量，那看着题多、每面其实都只有一道。
11. **「能不能赢」是选题三项联合判断（有需求 × 有资格赢 × 可交付）里的一项，不能单独用。** 判断方法是：**竞品优势若来自品牌知名度或广泛媒体共识，短期不可逆转，该方向只作基线；不来自共识的方向才是 90 天内可推进的战场**（见《售后生词规则》§4）。不能因为单次未提及或零提及就删题，那会污染可见度测量。
12. **内部映射不入可重排或对客产物**：题号↔证据位置、Case 字段↔题 这类对应关系只写在持有它的内部文件里。题号会随每次重排失效，写死进题库、证据文件或客户文档即埋雷。
13. 程序校验通过后仍要做人工语义复核，重点检查跑题、引导、事实扩张、中英文不等义和重复问题。
14. **代表性先于穷举**：写题前先做内部覆盖查漏，至少检查产品线、买家、旅程、市场/语言、约束、竞品/替代方案和业务优先级；这是一张内部工作表，不是客户填写表，也不产生笛卡尔积配额。
15. Prompt Task 至少从真实需要中选择：`Discovery`、`Problem Solving`、`Evaluation`、`Comparison`、`Alternatives`、`Shortlist`、`Validation`、`Transaction`、`Post-purchase Support`、`Category Understanding`、`Source Discovery`。不要求每批覆盖全部任务；没有独立业务问题就不生成。
16. 题型任务与分析路由分开。比较、替代、验证、交易和购买后支持不自动进入自然可见度；先按题面、品牌范围和用户任务选择现有 Intent 或独立合同，再写入 `Prompt Task`。

## 售前与售后的边界

售前默认先确定 Discovery V1，再按需补竞品与评价。每 Topic 至少 5 条、整批（含补题）不超过 50；没有固定补充题型配额。公开证据可以支持售前假设，但客户未确认时如实标记，不能把官网自述或 AI 扩展当成真人需求。

售后优先继承售前研究、客户确认文档、Topic、发现型问题和历史结果，补内部信息并校正，不默认从零重做。推荐首期 1 品类 + 2 细分，事实只支持 1 + 1 时不凑数；同一 Topic 应有至少 5 个独立发现型意图，否则补证据、合并或暂作 Tag。售前 50 条批次上限不等于售后永久词库上限。

## 阶段交接

复用现有字段和文件，交接信息不足时补记录，不另建平行业务配置。售前确认服务于初步诊断，客户未回复时可交付标为待确认的 V1；售后正式监测前必须继承并复核业务重点、产品/买家/市场范围及事实和不适用边界。试跑后的最终词组确认与这次范围确认分开记录。最低保留：

| 资产 | 交接信息 |
|---|---|
| Case 与客户文档 | 单产品线边界、Base Record、客户确认文档标识、版本、已确认内容与待补项；未知链接如实留缺，不能编造。 |
| 研究证据 | 来源/日期、原始表述或忠实摘要、事实/判断/假设状态、对应 Case 字段或选题理由。公共需求、客户原话、AI 回答分别标注。 |
| Topic 与问题 | 既有 Topic/Question ID、题面、购买意图、实际属性、来源、市场/语言和本次版本；不靠重命名生成新资产。 |
| 历史结果 | 原采集产物位置、平台/模型或模式、配置和采样时间；未采集记为待试跑，不生成结果或 Gap。 |
| 变更 | 保留/修改/新增/合并/归档及理由。修改语义时新版本关联旧问题，原题和数据保留。 |

这些信息写在现有交接记录中；缺少容器时使用独立 `handoff.json`，题级证据以 `question_id` 关联。不要往闭合题库 `config`、Base schema 或上传 CSV 静默加列。

Case 研究后由 Case Builder 生成预填客户确认文档；客户确认业务、市场、优势、边界并补充销售/客服/成交流失等真实意图。可用访谈、已有材料或脱敏摘录，降低填写负担而不是减少上下文。文档创建、客户未回复或只勾选“同意”都不能代替内部买家证据。需要逐条给客户核对属性池、相对竞品、优先级或候选监测问题时，按 `geo-after-sales-prompt-builder/references/client-facing-attribute-pool.md` 的对客件结构输出：品牌事实单独确认、属性池承载购买影响与相对竞品、候选问题单独确认、每张表都有 `客户确认` 列且空白表示无需修改。

## 试跑与基线

每个市场/语言先做代表性核验，再决定复用或改题。只有当地买家决策、品类含义、预期答案集合和证据生态足够等价时，才复用候选意图和 `intent_key`；否则按当地证据标记为 `localized`、`market_specific` 或 `not_supported`，调整、增加或暂不生成。不同语言按当地语言重写题面；预算/币种、当地竞品、购买约束、术语、法规、信任信号、平台/信源生态和购买预期都属于市场核验项。每个市场/语言仍有独立题库快照、版本和基线。同市场同语言的题面可跨平台复用，平台属于采集配置。完整覆盖表留在内部交接，客户只看到整理后的属性池和必要的市场差异。校验器通过只说明确定性门槛通过，不等于客户批准或已经试跑。

售后顺序为范围复核 → 每道候选题在拟监测平台各试跑 3–5 次 → 确认最终词组并锁版本 → 连续 3 天每天 1 次正式 Baseline。试跑只修正歧义、跑题、重复与诱导，不以本品是否出现选题；试跑结果不混入 Baseline。只使用同题、同市场/语言/平台及采集配置的有效样本；失败或缺日不能记为零或拼接成 3 天。三次观测建立初始基准，不证明长期稳定认知缺口，后续同口径监测再验证趋势。新增、删除或改词均另立版本，受影响的监测组单独重建 3 天基线；保留旧题和数据，不拼接新旧曲线。

品类 Topic 下的 Discovery 仍按日级基线/正常监测运行，不等于低频 Category Awareness。品类观察组不是自动成立的因果对照组，也可以在有证据的情况下成为优化方向。保留售前历史数据；效果比较只用同题、同条件、同口径的窗口，不因长期零提及淘汰仍有业务价值的问题。
