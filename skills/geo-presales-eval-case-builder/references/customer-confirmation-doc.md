# 客户确认 / 补全文档规则

完整 Case 默认准备一份预填的 Feishu 客户确认文档。它是研究交接与事实补全界面，不是把 AI 研究结果伪装成客户访谈，也不是审批记录。

## 文档目标

让客户快速确认研究范围并补充内部现实。预填内容可以帮助客户纠正已有执行上下文，例如目标市场、语言和 AI 平台，但这些不新增为 Case 字段。客户必须贡献真实买方语言或内部证据；可以用脱敏后的访谈记录、销售 / 客服材料、win-loss、GSC / 站内搜索、历史问答和其他已有资料替代长表逐项填写。只提供能改变判断的材料，不要求完整属性或用户旅程矩阵。**当交付物需要客户逐条核对属性、相对竞品和候选监测问题时，按售后 skill 的 [客户属性池与对客确认件规则](../../geo-after-sales-prompt-builder/references/client-facing-attribute-pool.md) 展开；本文件只定义 Case 确认骨架，不另造一套属性池格式。**

文档至少包含以下短节：

1. **研究范围与产品线**：品牌、单一产品 / 品类、适用边界、同一购买集合；列出已调研竞品的名称、官网和可替代理由，请客户确认或补充；标记 `已知证据 / 研究假设 / 待客户确认`。
2. **买方与执行上下文**：B2B 的目标企业画像（ICP）与目标客户（persona），或 B2C 的目标客户（audience）；目标市场与语言只作执行上下文，不新增 Case 字段。B2B 还要收集买方采购打分维度、需对接的系统类别与安全合规要求（购买标准 / 集成与兼容 / 信任与合规）。
3. **优先级与赢单边界**：本轮业务重点和 Topic 优先顺序、买家在意的购买标准、可验证差异化、不能服务的情况、能赢的场景、独有资产及其可引用位置。业务优先级与 Attribute P1/P2/P3 不混为一谈。属性优先级由我方先给初步分级（P1/P2/P3），交客户逐条核对或直接调整；门槛型属性（缺失会被直接排除出候选集合）可直接定为 P1。只有连“是否构成门槛”都无法判断时，才留待客户补充后定级，并用一句话说明缺什么才能定。
4. **建议监测主题**：1 个品类 Coverage + 默认 2 个不同购买场景 Depth；证据不足时为 1+1。每个主题写来源和假设，并确认能形成至少 5 个独立发现型购买意图；不分配每 Topic 题数或属性数。若本轮需要品牌方逐条核对属性、购买影响、相对竞品或候选问题，转用 `geo-after-sales-prompt-builder/references/client-facing-attribute-pool.md` 的对客件结构：品牌事实单独一张表，属性池一张表，候选监测问题另表，每张表保留 `客户确认` 列。
5. **客户必须补充**：真实买方意图 / 原话，以及脱敏后的销售、客服、win-loss、GSC / 搜索词、CRM、案例、评测、FAQ 等可用材料。没有材料时说明缺口，不用营销 USP 代填。
6. **确认状态**：逐项选择 `已确认 / 需修正 / 待补证据`。文档创建、预填、客户未编辑或沉默都不改变状态。

## Feishu 操作与更新

- 使用项目现有的 `lark-doc` / `lark-cli` 工作流和已授权身份；本 Skill 只定义内容与安全边界，不存放 URL、token、profile 或账号信息。
- 第 7 步先查找已有 Case 关联文档，优先通过现有 Record、品牌 + 业务 / 产品名称、已有 handoff URL 或文档身份定位，并读回原文。找到后在第 9 步更新原文档，不复制新客户文档。
- 更新时保留文档标题、URL / token、已有确认答案和客户材料；只重写受本轮研究影响的预填章节，并保留差异与待确认状态。
- Topic-only 更新只改建议主题、来源假设和受影响的边界章节；除非客户明确要求，不重复完整 onboarding。
- 用户明确离线时，不调用创建、编辑、分享、改权限或发消息；输出本地 Markdown / 内容草稿。其他完整 Case 默认在第 9 步使用既有身份创建或更新客户文档，并读回正文，返回实际 URL / token；创建、更新、读回或正文核对失败时，明确标为部分失败或阻塞。
- 不自动公开分享，不修改权限，不将客户的内部答案改写成公开来源或 AI 的断言。

## 预填标记

每个事实或判断旁标注一种状态：

- `已知证据`：来自客户材料、官方页面或可核验公开来源，附来源。
- `研究假设`：根据公开买方需求、场景语言或竞品 / 替代方案推断，明确写“待客户确认”。
- `待客户确认`：需要客户说明内部现实、优先级、实际赢单与不能服务边界，不能由沉默推定。

客户确认文档不追求字段、问题或属性配额；只收集能改变 Case 范围、主题、证据或下游 Prompt 设计的内容。下游首阶段只做 Discovery：每 Topic 至少 5 条独立发现型购买意图，售前整批不超过 50 条；竞品评价后补，不设固定配额。
