# 对客确认表（飞书多维表格）

对客确认件是从项目知识库模板《AI 搜索监测确认表（模板）》复制的飞书多维表格，每个客户一份，多个市场共用一份。复制后删掉所有【示例】行。品牌方要填的业务信息、要提供的数据和平台数据（默认品牌方导出文件上传；愿意开权限的再开 GSC 受限 / Bing 只读）统一用飞书文档[《AI 搜索监测｜品牌资料收集》]([内部链接已移除])收，每期只收一个市场、一种语言、一条产品线，每个品牌要的数据基本一样，Base 里不单列。模板不带使用说明文档：各列怎么读写在字段说明里，考核口径写在意图类型的字段说明里。

品牌方一定会读的是提示词库；业务范围是他们要确认的事实；主题、提示词矩阵可选读。所以提示词库要能独立看懂：每道题的主题、行的业务优先级、出题原因自带解释；需要品牌方回答的问题写在业务范围的【请品牌方补充】占位里，并在字段说明里告诉他们去哪看。

选词规则本身见 [selection-rules.md](selection-rules.md)；本文件只写表、字段和填法。

## 表

六张表，按这个顺序：

| 表 | 一行是什么 | 要点 |
|-|-|-|
| 业务范围 | 一条可以单独确认的事实 | 见下 |
| 品牌事实核查 | 一条官网自相矛盾、或只有自述没有外部佐证的事实 | 见下 |
| 需求信号 | 一条买家原话、搜索词或 AI 检索词 | 见下 |
| 提示词矩阵 | 一个处境的一种问法：产品线 × 市场 × 目标客户 × 使用场景 × 意图类型 | 唯一判业务优先级的地方，见下 |
| 主题 | 一个主题 × 一个市场 | 主题优先级在这里，见下 |
| 提示词库 | 一道提示词 | 品牌方一定会读，见下 |

基线结果不写进 Base，另出一份 HTML 报告（见 `geo-monitoring` → baseline-report.md）。

## 通用规则

- **品牌方直接改格子**：事实不对就改，缺了就加行。Base 里没有「客户确认」列。发出前给每张表存快照，回收时对照快照和 `lark-cli base +record-history-list` 看每处改动；重点看提示词矩阵「业务优先级」的改动。
- **编号一经发出就冻结**：切片编号（M-001…）和题号只追加不重排；删掉的题号不复用；合并主题不重编题号。生成脚本里的例外和映射用稳定值做键（切片用「产品线|市场|目标客户|使用场景|意图类型」，题用 `intent_key`），不用显示编号。
- **Base 只放在测的题**：试跑时删掉或改写的、锁版时没选的、正式题里后来停测的，都从提示词库删除，题号和原因记在题库 `config.retired`。删前存快照。
- **品牌方能看到 Base 之后只做增量部署**：不整表删了重建（会换掉 record_id，关联字段全断）。每次部署前后跑 `python3 -I <项目根>/.agents/skills/geo-prompt-selection-builder/scripts/diff_base_against_spec.py --base <token> --spec <spec.json>`（在客户目录下跑，lark-cli 只能写当前目录），0 差异才算部署完。默认主键：主题＝主题+市场，提示词矩阵＝切片编号，提示词库＝编号，需求信号＝输入编号，业务范围＝项目，需要品牌方提供的数据＝数据，品牌事实核查＝事实项。
- **多个市场共用一份 Base**：每张表在主字段后加「市场」字段。各市场都一样的事实写一行、市场多选；各市场不同的（官网路径、本地叫法、法规、别名、竞品）每个市场一行，同名放在一起。提示词按意图和语言合并：同意图同语言的一行多选市场；语言不同的每种语言一行（各自审核、各自挑正式题）。需求信号单选市场。只属于一个市场的编号带市场前缀（`KR-R001`、`AN-KR-T1-D01`），切片编号不带。每个市场在需求信号、提示词矩阵、提示词库各建一个筛选视图。测量仍按市场分开：题库 JSON、validator、版本、基线一个市场一份。
- **主字段按关联格里要显示什么来选**：需求信号以「原话」为主字段（品牌方只读中文时用「译文」），提示词库以「提示词」为主字段，提示词矩阵以「切片编号」为主字段。
- 不用合并单元格；空单元格在插行删行时更安全。

## 业务范围

一行一个事实，多值事实拆成编号行：产品线（n）、核心目标客户与购买场景（n）、主要目标客户（n）、使用场景（n）、竞品（n）、差异化优势（n）。单值行：品牌、品牌别名、官方域名、品类、市场与语言（语言＝买家向 AI 提问用的语言）、平台、适用边界（本期不覆盖的产品、渠道、客群或服务）。表头 `项目 | 内容 | 为什么重要`。品牌、品牌别名、官方域名、市场与语言、产品线、适用边界、竞品、核心目标客户与购买场景、差异化优势对应资料收集文档第一部分的字段，按品牌方填的写；品类、平台、主要目标客户、使用场景、社区平台与信源服务由我们填；主要目标客户、使用场景行名带「（我方填）」，和照品牌方资料转录的行分开。官网能查到的我们预填，品牌方核对；只有品牌方知道的、或品牌方填了「待补充」的，行首写【请品牌方补充】；品牌方填「无」的照写「无」。

- **产品线**：每期只做一条，品牌方在资料收集文档里填本期产品线，标（本期）；后续期新增的另附资料后加一行，标（后续）。
- **核心目标客户与购买场景（n）**：品牌方按业务优先级填最重要的几条，最优先的写第 1 条。每条写目标客户（服务什么样的买家：B2C 写客户人群；B2B 写企业类型、规模及决策或使用角色）和购买场景与需求（买家要解决什么问题、购买时重点关注哪些属性，我们据此整理约束条件）。原样记录，是主要目标客户和使用场景（selection-rules.md → 4）的起点，矩阵行的客群和需求列在这里的，判业务优先级时算本期重点。
- **主要目标客户（n）（我方填）**：我们从核心目标客户与购买场景出发，按调研拆、并、补，每处调整写依据，依据里的信号写输入编号。优先目标客户标「（优先）」；品牌方已填内容能看出来的我们代标，写「我方按品牌方已填内容推断，品牌方可改」。
- **使用场景（n）（我方填）**：紧跟主要目标客户之后。每行写一个使用场景（动宾短语，如「找转售组屋」「看新盘或 EC」）、哪类目标客户在做、依据是什么；定义和判断标准见 selection-rules.md → 4「使用场景」。和目标客户一起交品牌方确认，写题前冻结。矩阵的「使用场景」列选项从这几行来。
- **竞品（n）**：`名称（官网域名；适用：产品线 / 市场）：依据`，品牌方填 1–3 个（名称和官方域名），我们核对、不冻结，不足 3 个的试跑后按发现题答案补；每条产品线 × 每个市场默认 3 个、上限 5 个（selection-rules.md → 1）；依据只写提及类读数，不写「首推」「排第一」。直接竞品和替代方案不分开标；没有官网的写「无固定域名」。域名必填，引用统计按域名匹配竞品页。
- **品牌别名**：简称、旧名、本地语言名、常见拼写和空格变体；买家常直接叫的产品系列名或型号也列进来；容易混淆、不能算作本品牌的名称（同集团其他品牌、同名的其他公司）单独注明「易混淆、不计入」。行首写【请品牌方补充】，提及统计靠它。
- **官方域名**：品牌官网、相关子域名和市场独立站，每个注明用途；引用统计按这些域名认官方页面。没有官网的写「无」，品牌方改给线上页面清单（signal-sources.md → 客户提供什么）。
- **差异化优势（n）**：品牌方填本期产品相比主要竞品、买家能感知到的不同之处，如功能、性能、价格、服务或资源；竞品普遍也有的不算（正品保障、售后完善这类品类门槛）；只对特定客户或使用场景成立的注明适用范围；不要求证据；品牌在各条约束条件上相对竞品的位置，正式基线后对有缺口的题再判。业务范围里只用这一个名字，不另设「产品卖点」。
- 业务范围只设上面列出的行；目前只做发现型可见度（selection-rules.md → 1），不收目标选项。
- **社区平台与信源服务**（我方填）：记录品牌方可以参与的社区和可用发布资源，作为动作线索，另查具体页面能否被采纳。

## 品牌事实核查

`事实项（主字段） | 产品线 | 官方值 | 来源页面 | 冲突说法 | 冲突来源 | 品牌方要做什么`

一行一个官网自相矛盾、或只有自述没有外部佐证的事实，也收预跑、试跑里 AI 说错的品牌事实。品牌呈现本期暂停，调研时不专门做，顺带看到才记（selection-rules.md → 3「品牌事实核查」）。公开资料能定的事实写进业务范围，不进这张表。来源页面和冲突来源写完整网址，没有网址不立行。「品牌方要做什么」二选一：**改官网**（冲突全在品牌自己的渠道里）、**提供材料**（我们核实不了，需要第三方测试或证明）。

## 需求信号

`原话（主字段） | 译文 | 来源类型 | 目标客户 | 约束条件 | 出处 | 月搜索量 | 产品线 | 输入编号 | 引用它的问题`，默认按来源类型分组。

一行一条会改变选词判断的信号：买家原话（销售、客服、评价、社区）、搜索词（GSC、Bing、Google Ads、关键词工具、站内搜索、电商平台搜索、搜索联想；关键词工具按工具分选项）、AI 生成的检索与问题（Bing AI 检索词、query fan-outs、AI 追问、模型建议问题）和官网线索（品牌官网、竞品官网）。原始导出文件留在客户目录，只登记补出约束条件、撑起场景或目标客户、提供题面措辞的那条。每类数据进不进表、怎么用见 signal-sources.md →「每类数据怎么用」。

- **译文**：品牌方只读中文时填，原话已是中文的留空。
- **来源类型**（单选）：GSC / Bing / Google Ads / DataForSEO / Semrush / Ahrefs / Similarweb / Keyword Planner / Naver / 站内搜索 / 电商平台搜索 / 搜索联想（People Also Ask、相关搜索、自动补全）/ 销售 / 客服 / 评价 / 社区 / Bing AI 检索词（Bing Grounding Queries、Topics Portfolio 机会查询，背后是真实用户的提问）/ query fan-outs / AI 追问 / 模型建议问题 / 品牌官网 / 竞品官网。品牌官网、竞品官网是品牌自己写的内容（导航和专页、FAQ、指南、竞品强调的选择条件），只开假设级候选；官网上买家写的评价、问答记评价或社区（selection-rules.md → 2）。query fan-outs、AI 追问、模型建议问题由模型生成，背后不能确认有真实用户，也只开假设级候选：query fan-outs 是 AI 检索时拆出的子查询（采得到的是 ChatGPT `search_model_queries` 和 Grok `tool_usages` 里的检索词；GSC 里看得出是 AI 发出的检索也记这一类，出处写 GSC）；AI 追问是答案末尾 AI 反问的条件（「预算多少」「团队多大」；ChatGPT 有 `follow_up_form` 字段，其他平台从答案正文末尾读）；模型建议问题是平台在答案后推荐的延伸问题（Gemini `related_queries`、Grok `follow_up_suggestions`、Perplexity 相关问题），以及我们让模型列的买家顾虑、按人设设想的搜索词。按真实出处选，评价和社区不分是谁家的。**评价和社区按内容分，不按网站分**：买过、用过之后写的使用体验记评价（电商和应用商店评价、Trustpilot、Google 地图评价，也包括 Reddit 上的「用了三个月」帖），它说明哪些条件在实际使用里起作用、哪里让人失望；还没买时的提问、求推荐、比较讨论记社区（论坛、Reddit、Facebook 群、电商页的问答提问），它说明谁在问、在什么处境、怎么问。两类分开记，因为说明的东西不同：同一个条件买前有人问、买后有人评，比只出现在一边更可靠。官网上的评价要先确认是买家自己发的（selection-rules.md → 2「品牌官网」）。DataForSEO 到 Naver 六项是关键词工具，按数据实际从哪个工具导出选（品牌方给的 Semrush 导出选 Semrush，我们跑 `collect_keyword_data.py` 的选 DataForSEO），不同工具的搜索量估值可能差几倍，要能分开看。
- **约束条件**（多选）：登记时就填。一条信号可以挂多条（「卧室能放吗」同时挂运行噪声和气味控制）；只表达品类需求、对不上具体约束的留空。选项和提示词矩阵、提示词库是同一份名单（见下「约束条件」）。
- **目标客户**（多选）：这条信号是谁在问，登记时就填，看不出是谁的留空。选项和提示词矩阵「目标客户」、业务范围「主要目标客户（我方填）」是同一份名单，拆、并、改名时三处一起改（`check_client_base.py` 查是否一致）。
- 一条信号只在登记时判两样：目标客户（谁）、约束条件（在意什么）。预算、房型、地区这类具体取值留在原话里，写题时取；使用场景和意图类型在矩阵行上判。矩阵行有没有信号支撑由 `check_client_base.py` 按「目标客户相同、约束条件也相同」统计，不手挂；来源类型是 query fan-outs、AI 追问、模型建议问题、品牌官网、竞品官网的信号不算支撑。
- **出处**：能追溯回原始数据的位置。有网址写网址；没有网址的写「文件名＋位置」（「GSC 导出（2025-11~2026-10）第 37 行」「销售问题清单 第 5 条」）。评价写明是哪家的哪个商品；电商平台的汇总标签（Amazon「Customers say」）原话只留标签文字，商品名写在出处。
- **月搜索量**（单选：>10,000 / >1000 / >100 / <100）：只填真实搜索量，哪家关键词工具有数据就填哪家，来源类型就是那个工具。GSC、Bing、Google Ads 的展示量和站内搜索次数不是搜索量，不填；搜索联想不带量，留空。其他来源类型的行补查了量的，出处里写明量取自哪个工具（「搜索量：Ahrefs」）。
- **输入编号**放在靠后，品牌方和我们反馈时用它指一条信号。
- **引用它的问题**：提示词库「证据」的反向关联。

## 约束条件

不单设表。约束条件是需求信号、提示词矩阵、提示词库三张表共用的选项字段（多选），三处选项是同一份名单；改名、合并时三处一起改，`check_client_base.py` 查是否一致。

- 一条约束条件 ＝ 买家在几个选项之间比较、筛选的一个维度（「学校距离」「短租与灵活租期」）；买家任务（出租、装修、卖房）写成矩阵行，不当约束条件。粒度规则见 selection-rules.md → 3。
- 不判重要性、不判相对竞品：重不重要看它挂在哪些矩阵行上；品牌比竞品强还是弱，正式基线后对有缺口的题判。
- 品牌无法满足某个任务的硬条件、又没有补救通道的，不开行，记在题库 notes「没开的格子」，不进对客表。

## 提示词矩阵

`切片编号（主字段） | 市场 | 产品线 | 目标客户 | 使用场景 | 意图类型 | 约束条件 | 业务优先级 | 业务优先级依据 | 主题 | 已有问题`；单市场没有市场列。两个视图，都按业务优先级、再按切片编号排序：默认视图「本期出题」筛主题不为空；「完整矩阵」显示全部行，包括本期不出的行。

- **一行 = 产品线 × 市场 × 目标客户 × 使用场景 × 意图类型**，列出这一行买家看重的约束条件。同一个任务要用几种方式问就开几行。怎么开行（发现行用核心目标客户 × 使用场景查漏，组合成立就开，没证据标假设；其他类型有证据或合理假设才开）见 selection-rules.md → 5「意图类型：八类」。对客表放完整矩阵：本期不出题的类型的行也写进来。
- **切片编号**：纯文本 M-001、M-002…，按顺序，不用公式。
- **目标客户**：多选，选项来自业务范围的「主要目标客户（n）（我方填）」，和需求信号的目标客户是同一份名单。只写真实人群；没有细分人群写品类基础人群（「养猫家庭」），不写「通用」、不留空。几类目标客户问法和关注点一样才多选，否则拆行。
- **使用场景**：单选，选项来自业务范围的「使用场景（n）」：这类目标客户在什么情境下用产品、要解决什么问题（定义见 selection-rules.md → 4）。
- **约束条件**：多选，品牌相对较弱的也可以挂。
- **意图类型**（单选：发现 / 问题解决 / 评估 / 对比 / 替代 / 验证 / 交易 / 售后）：买家想完成什么任务，行上挂的题都是这个类型。定义和开行条件见 selection-rules.md → 5「意图类型：八类」和 type-branches.md；替代、对比行的开行依据（哪家竞品、哪条信号）写在业务优先级依据里。本期只做发现型可见度，只在发现行上出题；其他类型的行留给以后开放对应目标时用。
- **业务优先级**（高 / 中 / 低）和 **业务优先级依据**：根据一类买家需求对品牌的商业价值、战略重要性和当前业务重点的贡献判断（规则见 selection-rules.md → 5）。不打分、不套公式；证据多少、AI 现在提不提品牌、品牌比竞品强弱、品牌有没有内容都不拿来调档；意图类型只看它和本期目标对不对得上，定这一类行最高到哪一档。依据写一句，说明这个需求对哪项业务目标起什么作用。`write_prompt_reasons.py` 把依据带进每道题的出题原因。其他七类行最高到哪一档见 type-branches.md「业务优先级上限」，依据里写明对的是哪项目标。高、中的发现行出题，题数按决策差异定；低默认不出题，高、中档覆盖不够时可以补。
- **本期不出**：非发现行本期都不出题，看意图类型就知道，不用另写。低档发现行没挂题的，在业务优先级依据末尾写「本期不出：业务优先级低，原因……」；在「完整矩阵」视图里筛「业务优先级依据」包含「本期不出」就能看到这些行。`check_client_base.py` 查低档、没挂题的发现行依据里有没有「本期不出」。不属于本期范围、缺乏合理需求依据、品牌做不到又没有服务路径的处境不开行，不进矩阵（selection-rules.md → 5）。
- **主题**：链接主题表，行定完业务优先级、聚完主题后填；一行只属于一个主题（本期只有发现行挂）。
- **已有问题**：提示词库「所属切片」的反向关联，自动显示这一行挂了哪些题。
- 不设备注列：拆题理由写进每道题的出题原因，没有信号支撑的行在业务优先级依据里写「假设：……」，替代、对比行的开行依据和低档行本期不出的原因也写在业务优先级依据里。列只有上面这一行列出的。

## 主题

`主题（主字段） | 市场 | 产品线 | 主题优先级 | 主题优先级依据 | 父关键词 | 月搜索量 | 切片`，默认按主题优先级排。

- **主题**：中文名（「通勤耳机选购」「海外远程安全租房」），命名规则见 selection-rules.md → 6. 主题是什么。
- **采购情况不单设列**：看提示词库的「状态」，主题里有「正式」题即已采购。没选上或退出的主题保留行，原因写进主题优先级依据。
- **主题优先级**（高 / 中 / 低）和 **主题优先级依据**：不另做判断，默认取组内多数行的业务优先级（没有多数时人工判断并写理由）；同档先排发现类主题，再按父关键词月搜索量排先后（selection-rules.md → 6. 主题与主题优先级）。月搜索量哪家关键词工具有数据就填哪家，在依据里注明来源。主题表只有这一个依据字段，需求证据、代表搜索词和量都写在这里。
- **父关键词 / 月搜索量**：主题的需求证据。不设信号条数（条数取决于收集了几个来源、主题里有几行，不代表需求大小；没有信号支撑的情况在矩阵行一级查）。GSC 展示量不单设列：它取决于官网自己的排名，不参与排序；父关键词查不到搜索量时，可以在依据里写一句非品牌展示量，证明需求存在。
- **切片**：关联本主题的矩阵行；主题包含哪些处境看这里，不另写主题范围。
- 主题由我们命名和划分，业务范围里没有主题行。
- **主题边界可能在出题后调整**：主题是先按矩阵行聚候选、写完候选题才定稿的（selection-rules.md → 6「怎么聚」）。售前诊断报告上的主题名和边界，签约后做正式题集时会按售后重做一遍矩阵重新聚；个数差 1 个以内直接按新集合交付，差 2 个及以上或某个主题被整个并掉时，先书面告知再锁版。提示词库里还没有「正式」题的主题，边界都还没定死。
- 正式题总额度见 `geo-monitoring/references/trial-and-lock.md`「选正式题与锁版」（单个已采购主题不设上限）；候选主题不设题数底线和上限。

## 提示词库

`提示词（主字段） | 中文含义 | 状态 | 主题 | 意图类型 | 标签 | 所属切片 | 出题原因 | 证据 | 产品线`，默认按主题分组、组内按所属切片的业务优先级（高→低）再按编号排，「正式监测」视图同样设置（多市场时市场列紧跟提示词）；编号、约束条件、可改变性在表里但默认视图隐藏。这是品牌方一定会读的表。

- **主题**：从所属切片查找带出，不手填；主题表改名这里跟着变。
- **所属切片**：链接矩阵的一行。
- **标签**（多选）：跨主题切数据用，和上传 CSV 的标签同一套口径（selection-rules.md → 6「切片标签」）。我们填，品牌方不填：`python3 -I scripts/write_tags.py --base <token> --bank <bank.json>`（多市场重复 `--bank`，默认预览，`--write` 补选项、写入并回读）。品牌方想按别的方向看，记成自定义维度再重跑脚本，不在格子里手加。
- **约束条件**：多选，从所属切片的约束条件里选，第一个是主约束。品牌方点名的宽泛品类题留空，出题原因写「测品类整体格局」。
- **意图类型**：从所属切片查找带出（公式 `[所属切片].[意图类型]`），不手填；改类型在提示词矩阵改。一行只放一种类型，所以每道题的类型由它挂的行决定。题库 JSON 写 `prompt_type`，导出上传时换成线上的诊断意图（`diagnosis_intent`）；只有替代题（临时按 competitor 上传）在上传 CSV 的 tags 第一个写「替代」，其他类型不写进 tags。品类认知、准确性题不进提示词库。
- **状态**（待审核 / 需修改 / 已批准 / 正式）：一道题一生只用这一列。我们内部质检后标待审核；品牌方没问题或直接改好后标已批准，要我们改写标需修改。只有已批准的题进正式挑选。锁版时选中的改为正式，其他候选删除。
- **提示词库不设优先级列**：挑正式题的先后读「所属切片」带出的行业务优先级（selection-rules.md → 5）。品牌自己的读数（领先、落后）和品牌比竞品弱都不改行档位；题面条件落在品牌可核实的明显劣势里的，在出题原因结尾写风险提示（selection-rules.md → 7「品牌明显劣势的提示」）。
- **可改变性**（高 / 中 / 低 / 待试跑）：试跑后按这道题答案里被引最多的前 20 个域名判（规则见 `geo-monitoring/references/trial-and-lock.md`「试跑」），依据写在题库 JSON `changeability_basis`。
- **出题原因**：脚本写的一段话，回答「为什么出这道题」「为什么这个需求重要」：测哪类买家在什么处境下的什么需求、依据（按来源类型计数，加一条代表原话）、所在行的业务优先级及依据（本题新增的需求覆盖另说明）。用品牌方的话写（「买家挑工具时会因为它直接排除一个选项」），不写「证据强」。命令：`python3 -I scripts/write_prompt_reasons.py --base <token> --brand <题面里的品牌名> --noun <品类名词>`（默认预览，`--write` 写入并回读）。
- **证据**：链接需求信号。题面带了具体条件（预算、房型、地区）的，挂上取条件的那几条信号；不来自信号的条件写在题库 `condition_basis`。
- 正式题是一个视图（状态 ＝ 正式），不另建表。
- 各类型读什么指标、算不算考核（只有发现算）写在矩阵「意图类型」的字段说明里；认知差距和优化顺序是基线结果，写在 HTML 报告里，不进 Base。列只有上面这一行列出的。

## 品牌方要提供的数据

不在 Base 里列，品牌方按资料收集文档第二部分提供。原则不变：只要只有品牌方能拿到、而且会改变选词判断的数据（依据见 signal-sources.md → 客户提供什么，改清单时两处一起改）；GSC（非品牌查询，顶到 1000 行的另加 6 个词以上的长查询）、Semrush / Ahrefs / Similarweb（有订阅时）、销售常被问到的问题、客服高频问题（品牌方整理的清单，不要原始记录）这四项优先提供；Bing 建议开通、有数据时提供；Google Ads 搜索词、站内搜索词、GSC Generative AI Performance 选填；GA4 不再要；没有官网的改给线上页面清单和电商平台搜索词报告；公开能查到的搜索数据、评价、社区我们自己收。

## 写法

- 称「品牌方」，不称贵司、贵校。
- 直接写最终结论，不写「上一版」「补充更正」这类修订痕迹。
- 方法论、词频统计、验证步骤、证据对应关系留在内部文件，不进对客表。
- 题面里不写编号，爬虫用题面文字。
- AI 表现只写「推荐」「提及」，不写「首推」「排第一」或排名百分比。
- 只有 JS 渲染才看得到的数字，先说明来源限制，再当成 AI 读得到的证据。
- 公开资料能定的先自己核实（如某型号是否还在售：官网产品页、跳转、站内搜索，再看主要电商），结果写进业务范围，不问品牌方。
- 品牌方改事实和优先级（业务优先级、主题优先级），判断由我们做；不让品牌方替我们写理由（如「买家为什么认可这个优势」）。
- 文档格式的对客件（不是 Base 时）每张表加「客户确认」列，只在要改、要删、要加的行写，空着表示看过没问题。
