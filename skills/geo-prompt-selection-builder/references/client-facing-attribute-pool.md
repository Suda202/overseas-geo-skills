# 对客确认表（飞书多维表格）

对客确认件是从项目知识库模板《AI 搜索监测确认表（模板）》复制的飞书多维表格，每个客户一份，多个市场共用一份。复制后删掉所有【示例】行。品牌方要填的业务信息、要提供的数据和平台数据（默认品牌方导出文件上传；愿意开权限的再开 GSC 受限 / GA4 查看者 / Bing 只读）统一用飞书文档[《AI 搜索监测｜品牌方填写模板：业务范围与资料清单》]([内部链接已移除])收，每个品牌要的数据基本一样，Base 里不单列。模板不带使用说明文档：各列怎么读写在字段说明里，考核口径写在提示词类型的字段说明里。

品牌方一定会读的是提示词库；业务范围是他们要确认的事实；属性池、主题、提示词矩阵可选读。所以提示词库要能独立看懂：每道题的主题、提示词优先级、出题原因自带解释；需要品牌方回答的问题写在属性池「还缺什么」或业务范围的【请补充】占位里，并在字段说明里告诉他们去哪看。

选词规则本身见 [selection-rules.md](selection-rules.md)；本文件只写表、字段和填法。

## 表

七张表加一个看板，按这个顺序：

| 表 | 一行是什么 | 要点 |
|-|-|-|
| 业务范围 | 一条可以单独确认的事实 | 见下 |
| 品牌事实核查 | 一条官网自相矛盾、或只有自述没有外部佐证的事实 | 见下 |
| 买家原话 | 一条买家说法 | 见下 |
| 属性池 | 一条属性 | 只判相对竞品，见下 |
| 提示词矩阵 | 一个处境：产品线 × 市场 × 受众 × 场景 × 旅程阶段 | 唯一判业务重要性的地方，见下 |
| 主题 | 一个主题 × 一个市场 | 主题优先级在这里，见下 |
| 提示词库 | 一道提示词 | 品牌方一定会读，见下 |

基线结果不写进 Base，另出一份 HTML 报告（见 `geo-monitoring` → baseline-report.md）。

## 通用规则

- **品牌方直接改格子**：事实不对就改，缺了就加行。Base 里没有「客户确认」列。发出前给每张表存快照，回收时对照快照和 `lark-cli base +record-history-list` 看每处改动；重点看属性池「相对竞品」和提示词库「提示词优先级」的改动。
- **编号一经发出就冻结**：切片编号（M-001…）和题号只追加不重排；删掉的题号不复用；合并主题不重编题号。生成脚本里的例外和映射用稳定值做键（切片用「产品线|市场|受众|场景|旅程阶段」，题用 `intent_key`），不用显示编号。
- **Base 只放在测的题**：试跑时删掉或改写的、锁版时没选的、正式题里后来停测的，都从提示词库删除，题号和原因记在题库 `config.retired`。删前存快照。
- **品牌方能看到 Base 之后只做增量部署**：不整表删了重建（会换掉 record_id，关联字段全断）。每次部署前后跑 `python3 -I <项目根>/.agents/skills/geo-prompt-selection-builder/scripts/diff_base_against_spec.py --base <token> --spec <spec.json>`（在客户目录下跑，lark-cli 只能写当前目录），0 差异才算部署完。默认主键：主题＝主题+市场，提示词矩阵＝切片编号，提示词库＝编号，买家原话＝输入编号，业务范围＝项目，属性池＝属性，需要品牌方提供的数据＝数据，品牌事实核查＝事实项。
- **多个市场共用一份 Base**：每张表在主字段后加「市场」字段。各市场都一样的事实写一行、市场多选；各市场不同的（官网路径、本地叫法、法规、别名、竞品）每个市场一行，同名放在一起。提示词按意图和语言合并：同意图同语言的一行多选市场；语言不同的每种语言一行（各自审核、各自挑正式题）。买家原话单选市场。只属于一个市场的编号带市场前缀（`KR-R001`、`AN-KR-T1-D01`），切片编号不带。每个市场在买家原话、提示词矩阵、提示词库各建一个筛选视图。测量仍按市场分开：题库 JSON、validator、版本、基线一个市场一份。
- **主字段按关联格里要显示什么来选**：买家原话以「原话」为主字段（品牌方只读中文时用「中文意思」），提示词库以「提示词」为主字段，提示词矩阵以「切片编号」为主字段。
- 不用合并单元格；空单元格在插行删行时更安全。

## 业务范围

一行一个事实，多值事实拆成编号行：产品线（n）、主要受众（n）、核心使用场景（n）、竞品（n）、差异化优势（n）、业务目标（n）、营销活动（n）、核心可见度问题（n）。表头 `项目 | 内容 | 为什么重要`。官网能查到的我们预填，品牌方核对；只有品牌方知道的，行首写【请品牌方补充】。

- **产品线**：品牌方可以全列；建议本期先做一条，标（优先），其他标（后续）。
- **主要受众（n）**：品牌方先给，我们按调研拆、并、补，每处调整写依据。优先受众标「（优先）」；品牌方已填内容能看出来的我们代标，写「我方按品牌方已填内容推断，品牌方可改」。
- **核心购买需求（n）**：品牌方写「受众：最关注的问题、使用场景和购买标准」，是属性池和核心使用场景的候选，仍要买家证据核对。
- **核心使用场景（n）**：紧跟主要受众之后。每行写这个场景是谁、在什么处境下买、依据是什么。和受众一起交品牌方确认，写题前冻结。矩阵的「场景」列选项从这几行来。
- **业务目标（n）**：`目标（产品线 / 市场 / 受众；衡量方式）`。品牌方回答一句「核心业务目标是什么」，括号里我们按销售沟通补全。
- **营销活动（n）**：`活动名（时间；产品线 / 市场）：主推卖点`，只有品牌方知道，行首写【请品牌方补充】。活动卖点只作为属性池的候选，仍要买家证据；未上市的产品不写发现题；活动日期交给监测排采集计划。
- **竞品（n）**：`名称（官网域名；适用：产品线）：依据`，依据只写提及类读数，不写「首推」「排第一」。直接竞品和替代方案不分开标；没有官网的写「无固定域名」。域名必填，引用统计按域名匹配竞品页。
- **品牌与产品别名**：缩写、本地语言名、旧名、子品牌、常见拼错、同名的其他公司；行首写【请品牌方补充】，提及统计靠它。产品型号单独流通时才叫「品牌与产品别名」。
- **差异化优势（n）**：品牌方列卖点即可，不要求证据；相对竞品由我们判。
- **核心可见度问题（n）**：只写买家的问题本身，不写「问 AI」，不写希望 AI 怎么说。
- **希望解决的 AI 搜索问题**：品牌方写选项名（发现型可见度、竞争定位、品牌呈现、声誉与信任），问法见 selection-rules.md → 1. 确认业务范围；表单上不预选，发现题照常默认出；选了几项的按品牌方写的先后排，最在意的在最前。行首写【请品牌方补充】。
- **品牌方关心的问法（n）**：品牌方特别想看 AI 怎么答的问法原话；见过 AI 答错的，附上 AI 怎么说的。里面点名的竞品和说错的事实是出专项题、记品牌事实核查的依据。
- 选了不等于出题：除发现型可见度外，按 selection-rules.md 第 1 步的证据表判断出不出（品牌呈现的验证题写题时不出，只在试跑后按第 8 步的条件触发），出的题在提示词库的出题原因里写明依据，品牌方批准才进试跑。
- **社区平台与信源服务**（我方填）：品牌方用自己账号发帖的社区和另买的信源服务，判可改变性时这些算「社区」。

## 品牌事实核查

`事实项（主字段） | 产品线 | 官方值 | 来源页面 | 冲突说法 | 冲突来源 | 品牌方要做什么`

一行一个官网自相矛盾、或只有自述没有外部佐证的事实，在判相对竞品的同一轮调研里填。公开资料能定的事实写进业务范围，不进这张表。来源页面和冲突来源写完整网址，没有网址不立行。「品牌方要做什么」二选一：**改官网**（冲突全在品牌自己的渠道里）、**提供材料**（我们核实不了，需要第三方测试或证明）。

## 买家原话

`原话（主字段） | 中文意思 | 涉及品牌 | 来源类型 | 受众 | 旅程阶段 | 约束 | 来源说明 | 来源链接 | 收集日期 | 证据可信度 | 产品线 | 输入编号 | 月搜索量`，默认按旅程阶段分组。

- **约束**：2–3 个关键词，完整说法留在原话里。属性池的「常见约束」从这一列汇总。
- **月搜索量**（单选：>10,000 / >1000 / >100 / <100）：只给搜索数据行填，来自 `shared/scripts/collect_keyword_data.py` 或品牌方的关键词工具导出；取哪家的量见 selection-rules.md → 6. 主题优先级。自动补全行留空。
- **证据可信度**（高 / 中 / 低）：高 ＝ 品牌方一手记录（销售、客服、GSC、站内搜索）；中 ＝ 公开评价、社区原帖、关键词工具里有搜索量的词；低 ＝ 自动补全、People Also Ask、相关搜索、Google Ads 广泛匹配这类不确定是否是买家原意的。`write_prompt_reasons.py` 按它在同类来源里挑代表原话。
- **涉及品牌**（多选）：原话说的是哪家；泛泛的选购帖和搜索词写「未指明品牌」。
- **来源类型**：社区 / 评价 / 搜索数据，品牌方提供后加销售记录、客服记录、GSC、站内搜索。不写「竞品评价」，是谁家的写在涉及品牌里。
- **受众**：和提示词矩阵同一套选项；用哪家产品不是受众。
- **受众、旅程阶段两列用到才填**：只在这条原话被用作矩阵行的依据、或被选作代表原话时才填，空着不算欠账。
- 电商平台的汇总标签（Amazon「Customers say」）原话只留标签文字，商品名写在来源说明。
- **输入编号**放在靠后，品牌方和我们反馈时用它指一条原话。

## 属性池

`属性（主字段） | 相对竞品 | 类别 | 常见约束 | 品牌取值 | 判据与证据 | 还缺什么 | 产品线`，默认按类别分组。不设优先级、重要性、可改变性列。

- **属性**：一条属性一个名字，矩阵的「属性关联」显示它；全书只用这一个名字。
- **类别**：十二类查漏的标签（品类、产品特性、选购标准、差异化、信任与合规、限制与边界、地理与市场、使用场景……）。没有「受众」类。
- **相对竞品**（优势 / 持平 / 劣势 / 待确认）：品牌在这条属性上的真实行业位置。和业务范围里这条产品线、这个市场的竞品比；真正的对手不在名单上时，在判据里点名。位置因市场而不同时，按市场拆行。
- **常见约束**：买家提到这条属性时常带的条件和说法，写来源。写题时题面条件从所在行挂的属性的常见约束里取。
- **品牌取值**：品牌的实际值和出处页面。不进题面。买家侧属性没有品牌值的留空。
- **判据与证据**：开头写「相对竞品（持平）：和谁比，比什么事实」，如「持平：与 X、Y 比，三家都支持 Z」。优势、持平、劣势必须有这一行依据（`check_client_base.py` 会查）；待确认可以先空着，写明缺什么材料。试跑或预跑发现的写「试跑发现：…」「AI 错误：…」。
- **还缺什么**：只写品牌方才能回答、而且现在就会改变出题或判断的问题（相对竞品没定、某项业务或能力有没有、有没有补救通道）。品牌方筛「还缺什么」非空就能看到要回答的格子。做内容需要的材料等基线后再要，验证题的标准答案等试跑触发验证题时再要。官网和 App 能看到的不问。
- **产品线**：只有一条产品线也保留，后续周期会加。
- 劣势属性留在池里，可以挂在矩阵行上，写题时剔除。品类门槛（所有正规选项都满足的）不单列，相关顾虑归到真正起作用的属性。

## 提示词矩阵

`切片编号（主字段） | 市场 | 产品线 | 受众 | 场景 | 旅程阶段 | 属性关联 | 业务重要性 | 业务重要性依据 | 主题 | 已有问题 | 备注`；单市场没有市场列。两个视图，都按业务重要性、再按切片编号排序：默认视图「本期出题」筛主题不为空；「完整矩阵」显示全部行，包括本期不出的行。

- **一行 = 产品线 × 市场 × 受众 × 场景 × 旅程阶段**，列出这一行买家看重的属性。怎么开行（核心受众 × 核心场景 × 三段全面梳理，组合成立就开，没证据标假设）见 selection-rules.md → 5。
- **切片编号**：纯文本 M-001、M-002…，按顺序，不用公式。
- **受众**：多选，和买家原话同一套选项。只写真实人群；没有细分人群写品类基础人群（「养猫家庭」），不写「通用」、不留空。几类受众问法和关注点一样才多选，否则拆行。
- **场景**：单选，选项来自业务范围的「核心使用场景（n）」。
- **旅程阶段**：三段，见下节。对客表放完整矩阵：我们全面梳理出的需求认知、购买决策行都写进来。需求认知、购买决策行的备注写依据（对比题写竞品和买家在比的证据，评价题写可信度信号；没有证据的标假设）。
- **属性关联**：链接属性池，可以挂多条，劣势属性也可以挂。
- **业务重要性**（高 / 中 / 低）和 **业务重要性依据**：只看这类受众在这个场景、这个阶段对品牌方业务有多重要，依据写一两句（核心可见度问题、业务目标、营销活动、优先受众）。`write_prompt_reasons.py` 把依据带进每道题的出题原因。高、中都出题，题数按决策差异定，高的题提示词优先级更高；低本期不出题。旧客户 Base 的「优先级」字段和 P1 / P2 / P3 不改不迁移。
- **本期不出**：本期不出题的行，原因写在业务重要性依据末尾，格式「依据……。本期不出：……」，按原因分两种：
  - 没选对应目标：「本期不出：品牌方未选竞争定位；选了可在此行出对比题（有证据的竞品：X、Y）」，写明选哪个目标、这一行能出什么题，方便品牌方加购时判断；
  - 业务重要性低：「本期不出：业务重要性低，原因……」。
  两种都不写进备注，在「完整矩阵」视图里筛「业务重要性依据」包含「本期不出」就能看到全部本期不出的行。`check_client_base.py` 查需求认知、购买决策行没挂题的、和业务重要性为低的行，依据里有没有「本期不出」。
- **主题**：链接主题表，行定完业务重要性、聚完主题后填；一行只属于一个主题。
- **已有问题**：提示词库「所属切片」的反向关联，自动显示这一行挂了哪些题。
- **备注**：拆题理由（「除味：① 两三只 ② 四只以上」）、对比和替代题点名竞品的依据。本期不出题的原因不写这里，写在业务重要性依据末尾（见上「本期不出」）。
- 不设目标题数、覆盖情况、约束、可改变性列。

### 旅程阶段：三段，买家原话、矩阵、提示词库同一套

各阶段的定义和依据举例见 selection-rules.md → 5，各阶段允许出哪些提示词类型见 selection-rules.md → 7（validator 按它校验）。这里只给填表时对照的例句：

| 阶段 | 例 |
|-|-|
| 需求认知 | Why does my apartment still smell like cat litter even though I scoop every day? |
| 方案考虑 | Which automatic litter boxes work for three cats in a small apartment? |
| 购买决策 | Pbrand vs Litter-Robot: which is better for multiple cats? |

## 主题

`主题（主字段） | 市场 | 产品线 | 状态 | 主题优先级 | 主题优先级依据 | 父关键词 | Google 月搜索 | GSC 展示 | 买家原话条数`，默认按主题优先级排。

- **主题**：中文名（「通勤耳机选购」「海外远程安全租房」），命名规则见 selection-rules.md → 6. 主题是什么。
- **状态**：候选（在试跑）/ 已采购（正式监测）/ 停测（没选或退出）。停测的主题保留行，原因写进主题优先级依据。
- **主题优先级**（高 / 中 / 低）和 **主题优先级依据**：怎么判、同档怎么排见 selection-rules.md → 6. 主题与主题优先级。不是 Google 的月搜索量也填在「Google 月搜索」列，并在依据里注明来源。主题表只有这一个依据字段，需求证据、代表搜索词和量都写在这里。
- **父关键词 / Google 月搜索 / GSC 展示 / 买家原话条数**：主题的需求证据。原话为 0 的在主题优先级依据里标「待验证」。
- 主题由我们命名和划分，业务范围里没有主题行。
- 已采购主题的正式题最多 10 道；候选主题不设题数底线和上限。

## 提示词库

`提示词（主字段） | 中文含义 | 提示词类型 | 状态 | 主题 | 所属切片 | 提示词优先级 | 出题原因 | 证据 | 产品线`，默认按主题分组、组内按提示词优先级（高→低）再按编号排，「正式监测」视图同样设置（多市场时市场列紧跟提示词）；编号、属性、可改变性在表里但默认视图隐藏。这是品牌方一定会读的表。

- **主题**：从所属切片查找带出，不手填；主题表改名这里跟着变。
- **所属切片**：链接矩阵的一行。
- **属性**：链接属性池，这道题测的那一条，从所在行的属性关联里选；不能是劣势属性。品牌方点名的宽泛品类题留空，出题原因写「测品类整体格局」。
- **提示词类型**（发现 / 替代 / 对比 / 评价 / 验证 / 问题解决）：题库 JSON 的 `prompt_type` 的中文显示，名称见 shared/canonical-intent-mapping.md。我们填，品牌方不改。品类认知、准确性不进提示词库。
- **状态**（待审核 / 需修改 / 已批准 / 正式）：一道题一生只用这一列。我们内部质检后标待审核；品牌方没问题或直接改好后标已批准，要我们改写标需修改。只有已批准的题进正式挑选。锁版时选中的改为正式，其他候选删除。
- **提示词优先级**：可编辑单选，`write_prompt_reasons.py` 按所在行的业务重要性预填，可改变性为低再降一档。它只决定挑正式题时的先后，低档的题照样留在候选里。谁都可以改，改了的在出题原因结尾写「改档：理由，定为 X」（`check_client_base.py` 会查）。品牌自己的读数（领先、落后）不改优先级。
- **可改变性**（高 / 中 / 低 / 待试跑）：试跑后按这道题答案里被引最多的前 20 个域名判（规则见 selection-rules.md → 8. 试跑），依据写在题库 JSON `changeability_basis`。
- **出题原因**：脚本写的一段话，回答「为什么出这道题」「为什么是这个提示词优先级」：测哪类买家在什么处境下的什么需求、依据（按来源类型计数，加一条代表原话）、为什么是这个档位（所在行的业务重要性依据，可改变性降档另说明），结尾「提示词优先级：高」。用品牌方的话写（「买家挑工具时会因为它直接排除一个选项」），不写「证据强」。命令：`python3 -I scripts/write_prompt_reasons.py --base <token> --brand <题面里的品牌名> --noun <品类名词>`（默认预览，`--write` 写入并回读）。
- **证据**：可以链接买家原话，选填；条件的依据在属性池「常见约束」。
- 正式题是一个视图（状态 ＝ 正式），不另建表。
- 不设库分层、看什么指标、AI 认知差距、优化顺序列：各类型看什么指标、算不算考核（发现和替代算）写在「提示词类型」的字段说明里；认知差距和优化顺序是基线结果，写在 HTML 报告里。

## 品牌方要提供的数据

不在 Base 里列，品牌方按填写模板第二部分提供。原则不变：只要只有品牌方能拿到、而且会改变选词判断的数据（依据见 signal-sources.md → 客户提供什么，改清单时两处一起改）；GSC 和 Bing Webmaster 优先提供（默认品牌方导出，取最长历史）；销售与客服记录优先提供（整理好的摘要即可）；其余有就提供；公开能查到的搜索数据、评价、社区我们自己收。

## 看板「覆盖分布」

模板自带一个看板：一段怎么读的说明；提示词总数、已批准提示词两张卡片；按旅程阶段、按受众、按提示词优先级、按提示词类型（都数提示词库的题）；按主题 × 提示词优先级（先按主题、再按提示词优先级分组）。发 Base 和试跑前看一眼：有没有空着的阶段，主要受众或产品线是不是 0。

## 写法

- 称「品牌方」，不称贵司、贵校。
- 直接写最终结论，不写「上一版」「补充更正」这类修订痕迹。
- 方法论、词频统计、验证步骤、证据对应关系留在内部文件，不进对客表。
- 题面里不写编号，爬虫用题面文字。
- AI 表现只写「推荐」「提及」，不写「首推」「排第一」或排名百分比。
- 只有 JS 渲染才看得到的数字，先说明来源限制，再当成 AI 读得到的证据。
- 公开资料能定的先自己核实（如某型号是否还在售：官网产品页、跳转、站内搜索，再看主要电商），结果写进业务范围，不问品牌方。
- 品牌方改事实和优先级（业务重要性、主题优先级、提示词优先级），判断由我们做；不让品牌方替我们写理由（如「买家为什么认可这个优势」）。
- 文档格式的对客件（不是 Base 时）每张表加「客户确认」列，只在要改、要删、要加的行写，空着表示看过没问题。
