# Aleyda《怎么搭一个有代表性的 AI 搜索提示词库》21 步 vs 我们的流程

对照源：Aleyda Solis《How to Build a Representative AI Search Prompt Library》（https://www.aleydasolis.com/en/ai-search/ai-search-prompt-library/，2026-06-17 版）。她的 21 步分 4 部分；我们的流程是售前（Case → 属性池 → 初步优先级 → 候选题）+ 售后六步（属性池确认 → 初步优先级 → 候选主题与 Prompt → 试跑（各监测平台 3 次）→ 排序与选词 → 正式题锁版）。

> 注意：她的内容优化清单（AI Search Optimization Checklist）是另一篇文档，不在这 21 步里；内容执行由我方内容生产团队负责，数据分析侧只给优化方向（见 [gap-cause-action-table.md](../../geo-monitoring/references/gap-cause-action-table.md)）。

## 逐步映射

### 第 1 部分：定义这个库该代表什么（1–5）

| 她的步骤 | 我们的覆盖 | 说明 |
|---|---|---|
| 1 从业务问题出发 | ✅（10-14 补齐） | Case 必填字段 + 售后 Step 0 范围确认；representative-library.md 新增「Start From Business Questions」，补上之前缺的两项：**转化路径**（购买/线索/注册/演示/预订/订阅/到店）和**不同受众是否问法、术语、备选方案不同** |
| 2 梳理细分维度（产品线/受众/市场/优先级） | ✅ | 五维拆分规则（产品线不同拆 Case）、ICP 规则「目标企业画像决定一整组决策点」、市场与语言是生词维度 |
| 3 按商业模式选提示词类型 | ✅ | B2B/B2C 属性骨架分线（售后 SKILL Step 3 表）；行业典型决策摩擦列（signal-sources.md） |
| 4 覆盖关键旅程阶段 | ✅ | 旅程阶段八段（发现/解决问题/评估/对比/替代方案/验证/交易/购后支持），提示词矩阵、提示词库、买家原话三表同一套；10-15 起替换旧的五阶段 |
| 5 先搭提示词矩阵 | ✅ 两张表，链接（10-15 定稿，10-20 复核，10-22 补自上而下枚举） | 对客 Base 的「提示词矩阵」一行 = 覆盖切片 × 测的属性，首列切片编号（M-001…），切片维度对齐她的受众、旅程阶段、约束；她 Prompt Type 刻意不设（10-15）：各取值大多与旅程阶段一一对应，其余与约束、属性列重复，读结果的方式改由提示词库的「提示词类型」决定——注意她的 Prompt Type（问法形状：候选名单/品牌 vs 竞品/哪里买）和我们 10-22 定名的「提示词类型」（指标路由：发现/竞品/评价…）是**重名不同义**，对照她的文章时别当成同一字段。属性判断本身在独立的「属性池」表里判一次（相对竞品、可改变性、还缺什么、判据与证据），矩阵通过「属性关联」挂过去，可改变性是公式带出；重要性判一次写在池里（10-22 起；此前的切片级购买影响列已删，处境差异用拆属性行表达）。10-20 之前曾把属性池并进矩阵，两套结构并存后改成 link。目标题数、覆盖情况按她的 Target / Coverage 加回，批准数内联进覆盖情况公式；可改变性、优先级都在行上（公式带出）。没配题的属性也占一行、目标题数留空、原因写在备注。业务优先级、买家任务、去向列已删。不按笛卡尔积配题。**10-22 起补上她矩阵的「暴露覆盖缺口」用途**：骨架（产品线 × 受众 × 旅程阶段）在收信号前自上而下写全，信号往格子里填，矩阵定稿时仍空的格子用 `scripts/check_matrix_coverage.py` 列出、逐格写原因进内部交接件（此前自下而上，证据没采到的维度格子根本不出现，缺席不可见——Hbrand 回放 40 格空 19，出租业主 6 个阶段全空无人点名） |

### 第 2 部分：搭提示词集合（6–11）

| 她的步骤 | 我们的覆盖 | 说明 |
|---|---|---|
| 6 加上真实的买方约束 | ✅（10-22 补门禁） | 限定属性四槽位（无限定/目标用户/偏好标准/约束）；保留每 Topic 至少一条自然低条件题——她的原则是「刻意混用无约束和有约束」，无约束题当品类可见度的锚。10-22 起 validator 按 constraint_type 逐 Topic 警告全条件化的 Topic；领导者即默认的品类（after-sales-rules.md）写 `config.leader_default` 带原因作显式豁免（Hbrand 即此例） |
| 7 从多个来源取真实受众语言 | ✅ | signal-sources.md 四类来源 + 客户提供什么表 + 脱敏规则；10-14 补了用户原话的逐条记录格式（对应她工作簿的「受众输入」表），每道题的证据引用输入编号 |
| 8 搭提示词组，不要只有单条 | ✅ | Topic 为主组织单元 + Attribute/tags；分析单元是 Topic/Attribute 不是单条 Prompt |
| 9 只在能测出差异时才造变体 | ✅ | 去重单位是购买决策：best/top、同义改写不算新题；买家/地区/场景/决策阶段变了才算 |
| 10 按行业补买方不确定性 | ✅ | signal-sources.md「典型决策摩擦」列（2026-10-14 加） |
| 11 按市场本地化，不只翻译 | ✅ | representative-library.md 市场核验（共享/本地化/市场专属/不生成）+ 测试语言按买家决策语言定 + 题面默认不加地点（2026-10-13 加） |

### 第 3 部分：把衡量做得站得住脚（12–18）

| 她的步骤 | 我们的覆盖 | 说明 |
|---|---|---|
| 12 平台分开记，不混分数 | ✅ | 平台不影响生词、结果按平台分开报；正式可见度只统计 Discovery |
| 13 定抽样与衡量规程 | ⚠️ 有一项待确认 | 正式基线每个 query × 平台 × 国家 × 语言 30 次（2026-10-23 起；之前统一每题每平台 5 次）、是否跨天按项目约定、conditions_key 固定市场/语言/平台/口径、失败不记零。她的窗口是 24–72 小时，我们允许一次跑完或分几天，是刻意放宽（Suda 2026-10-13：样本次数够就行）。**会话状态未知**：她要求默认登出、无历史的干净会话；Scrapeless 文档没写采集时是否登录、是否带记忆，需向供应商确认后写进采集口径 |
| 14 定提示词总量（单产品 30–60 起步） | ⚠️ 刻意不同 | 她按业务复杂度给区间；我们按交付范围定：单产品线单市场总量沿用她的 30–60，其中核心层 20–30 条就够（Suda 2026-10-23）；售前每 Topic ≥5、整批上限 60 不变；售后候选主题不限数、每主题 ≥5，正式题每采购主题 ≤10。口径差异来自立场：她偏测量覆盖，我们卖交付结果 |
| 15 平衡品牌词/非品牌词/竞品词配比 | ⚠️ 刻意不同 | 我们不设配比配额：首期全部非品牌 Discovery，Competitor/Evaluation/Accuracy/Category Awareness 按证据与独立合同按需补，不为凑类型出题。她表里「发现型可见度以非品牌为主」与我们一致 |
| 16 有意识地加入竞品和替代方案 | ✅ | 正式竞品冻结 + Topic 局部边界（topic_ids）+ 替代方案/现状；10-14 补了容易漏的几类：聚合站与评价平台、免费/开源/自助方案、本地玩家、销售最常听到的品牌 |
| 17 给每条提示词打元数据 | ✅ | v8 逐题字段（question_id/topic_id/tags/analysis_type/intent_key…）+ 售后 JSON 合同；她的结果字段（出现/推荐/引用/描述准确）对应我们采集层与报告层 |
| 18 放大前人工抽检 | ✅ | 质量门 + 二遍语义 review + validator；10-14 在 representative-library.md 加了候选基线前的人工抽检清单（2026-10-23 候选基线取消后改为试跑前）（像不像真人、是否偏向某个旅程阶段、竞品集合是否真实、有无无意义微变体等） |

### 第 4 部分：把发现变成行动（19–21）

| 她的步骤 | 我们的覆盖 | 说明 |
|---|---|---|
| 19 缺口—原因—动作表 | ✅ | [gap-cause-action-table.md](../../geo-monitoring/references/gap-cause-action-table.md)；10-14 补了她表里我们缺的 6 类（被提及没被推荐、只被第三方引用、被描述错、本地竞品主导、产品细节缺失、一类受众/产品线缺席），每条方向写负责人和验证方法；SKILL Step 14 基线后交内容团队 |
| 20 定义刷新节奏 | ✅ | 版本化规则：增删改词另立版本、受影响组重建基线、不拼接新旧曲线；平台重大变化重建基线。按题型分三档（2026-10-26，参照她的节奏：品牌描述与认知每月复核、竞品对比每月或每季度、价格和可用性等重大变化后复核）：非品牌发现每天 1 次，作考核指标；对比、替代、评价每月复测，高风险声誉题可加密；验证、准确性只在事件触发时复测（初次诊断、发现错误、修复上线后、重要产品信息变化）。所有候选题都先过试跑（各平台 3 次），品类认知、准确性不占正式题名额。频率表在 geo-monitoring → 采集频率与重跑 |
| 21 核心/实验/监测三层 | ✅ | 2026-10-15 起按她的用途逻辑给每条候选题分层（规则见 representative-library.md → Roles and Refresh）：核心=非品牌发现/选择题，只有它进自然可见度趋势，也只有它组成每期跑的正式题；实验=价格库存配送、新市场/新产品线/新人群、fan-out 新方向、品类认知；监测=点名品牌的对比、评价、准确性。实验和监测层按第 20 步的触发条件重跑，不每期跑；推荐品牌方优先买核心层 |

## 结论

**21 步全部有对应。** 10-14 按她的原文补齐了第 1、5、7、16、18、19 步的缺项；10-22 再补三处：第 5 步的自上而下骨架枚举与空格子审计（`check_matrix_coverage.py`）、第 6 步的每 Topic 低条件锚题门禁（`leader_default` 为显式豁免）、主题聚类留痕（`config.topics` 的 `covered_attributes`/`planned_prompts`，先定主题后写题可核查）。剩下的差异是刻意取舍或待确认：

1. 衡量窗口放宽（第 13 步）——样本次数够即可，不卡 24–72 小时。
2. 会话状态待确认（第 13 步）——要问 Scrapeless 采集时是否登录、是否带记忆。
3. 题量按交付范围（第 14 步）——单产品线单市场总量 30–60、核心层 20–30（2026-10-23），售前整批上限 60 不变；售后正式题每采购主题 ≤10 不变。
4. 不设品牌词配比（第 15 步）——Discovery-first + 按需补充。
5. 核心层每天跑，对比、替代、评价每月复测，验证、准确性按事件触发（第 20、21 步，2026-10-26）；推荐品牌方优先买核心层。

她的流程适合品牌自己搭自用监测库；我们多出来的环节（各平台试跑后排序选词、正式基线每格 30 次、正式题锁版、客户确认件；2026-10-23 前还有候选基线）来自服务商要对交付结果负责。执行以本 skill 为准。
