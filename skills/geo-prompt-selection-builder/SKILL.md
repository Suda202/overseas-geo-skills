# GEO Prompt Selection Builder（选词）

## Purpose

选词决定测哪些题：售前选词工具（调研 → 属性分级 → 候选主题 → 确认件 → 候选题集），读试跑结果（各监测平台 × 3 次）排序、由客户选正式题并锁版本，以及签约后根据监测结果和业务变化补充、合并、淘汰 Prompt。跑基线、按期采集、出报告归 `geo-monitoring`（2026-10-22 拆出）。2026-10-22 起由「售后生词」改名为「选词」：这套方法早已前移给售前选词工具用，只叫售后已名不副实。它也是写题规则的唯一来源，`geo-presales-prompt-builder`（前置售前诊断）的写题规则与门禁引用本 skill。目标是发现新的可优化机会和细分分析视角，而不是把覆盖面机械做满。

Use this skill when the user asks to research and select a GEO Prompt set for a new client, or to create, revise, expand, prune, organize, or schedule a monitoring Prompt set. Read [after-sales-rules.md](references/after-sales-rules.md) before designing Topics or Prompt quotas. Read [representative-library.md](references/representative-library.md) when the task involves market/language coverage, attribute-pool gap checking, Prompt groups, localization, or sampling protocol. Read [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md) when producing or updating the client confirmation Base (使用说明 + 业务范围 / 品牌事实核查 / 买家原话 / 属性池 / 提示词矩阵 / 提示词库 / 需要品牌方提供的数据; competitors are 竞品（n） rows in 业务范围), an 属性池 or 对客确认件, or any customer-facing handoff. Read [output-contract.md](references/output-contract.md) when producing JSON, CSV, cadence, or audit artifacts. Two method-mapping references: [aleyda-21-step-mapping.md](references/aleyda-21-step-mapping.md) tracks coverage against Aleyda's 21 steps, [peec-geobubbles-ahrefs-mapping.md](references/peec-geobubbles-ahrefs-mapping.md) maps Peec / GeoBubbles / Ahrefs concepts to ours; consult them when auditing method coverage or translating an external methodology's term.

## Operating Boundary

- **Selection and monitoring:** start from existing data, real queries, AI answers, business changes, and content opportunities; preserve valuable existing Prompts and explain additions/removals.
- **Early presales diagnosis:** use `geo-presales-prompt-builder` for the one-off diagnosis bank (public evidence only, no confirmation Base, at most 60 Prompts). It follows this skill's writing rules; only its stage differences live there.
- **Out of scope:** defining metric calibers (owned by `geo-presales-report-editor` core) or sentiment rules (owned by `geo-presales-sentiment-judge`), crawler collection, baselines and reports (all in `geo-monitoring`), written report conclusions, and competitor discovery or freezing. This skill hands monitoring the Prompt set and collection plan; it reads the readings back to select and maintain Prompts.
- A frozen competitor list may be consumed for comparison Prompts, but this skill must not silently select, replace, or verify competitors.

## Required Inputs

Accept the inputs available in the current task; do not invent a parallel business schema.

- Existing monitoring Prompt set and its Topics, if available.
- Brand/product Case and the official domain.
- At least one real signal: existing monitoring results, GSC/SEO query data, AI-answer gaps, sales/customer language, customer-review language, CRM/customer-success findings, a new product/market/USP/audience, or an industry change.
- Region and language for the monitoring run.
- The business goal for this service period and the marketing campaigns inside it (业务目标 / 营销活动 rows in the client Base 业务范围, Suda 2026-10-23). They decide where the Prompt count goes and rank the audiences; they are never buyer evidence and never license a Prompt by themselves (client-facing-attribute-pool.md → *Settled table set*).
- Frozen competitors and their Topic boundaries when competitor Prompts are requested.
- Reusable researched context and a customer-confirmation document, when
  available; otherwise create a staged handoff artifact before formal lock.

Presales may leave the researched Case as a pending-confirmation V1. Before the
trial, the customer must confirm the current business priority,
product/buyer/market scope, and factual and exclusion boundaries. This is
separate from approving the formal Prompt set after the trial and ranking; record both
decisions. If presales confirmation already exists, review changes rather than
asking the customer to start over.

If the user only provides a product brief with no after-sales signal, build a
clearly labelled first hypothesis set and list the evidence that still needs
confirmation. It may support Discovery/Diagnostic exploration, but is not
formal-baseline-ready. Do not present LLM-invented expansions as high-frequency
demand.

## Customer and Market Signals

After-sales Prompt work should start from **signal collection**, not from a product feature list and not from a finished attribute list. Signals are what we gather; the Attribute Matrix is what we distil out of them. Before attributes and their importance are settled, collect user language from all four sources — **search data, sales records, reviews, and community** — reusing what already exists and filling whichever is missing. The client supplies the data only the brand party can access — sales and CRM records, support tickets and chat logs (asked first — a summarised version from the brand party is enough), plus GSC queries (especially high-ranking, low-CTR long tail), site and help-centre search, AI referral traffic from GA4 plus Bing Webmaster Tools (grouped with Search Console: query data and the whole AI Performance report), and its own testimonials (if available). Ask only for data that changes a Prompt-generation judgement, and word the client list as 优先提供 / 有就提供, never 必须给 — the dropped items are listed in signal-sources.md → 客户提供什么; we collect search data (non-branded demand, PAA and related searches, keyword tools), reviews (product and competitor reviews), and community language (Reddit, forums, industry communities). Strip names, emails, phone numbers, account IDs and customer company names from client records before turning them into buyer language, follow the brand party's privacy and data-use rules, and keep raw records internal — never in the bank or the handoff. Which sites to use depends on the industry and the market, and the full client-data list is in the same file — see [signal-sources.md](references/signal-sources.md). Every P1 / P2 needs at least one source; a row with none is marked hypothesis grade. Signals to gather:

- sales and CRM language, including why customers bought, did not buy, switched, renewed, or churned;
- customer-support and customer-success questions, misunderstandings, adoption barriers, and recurring service concerns;
- customer-review and public-discussion language;
- GSC/SEO queries as demand clues, never as Prompts copied without interpretation;
- customer role, business scenario, decision stage, constraints, and the decision or risk the question is trying to resolve.

The customer must supply a **signal pass** of their own: based on their sales, support, win/loss, and churn records, what their target buyers actually ask, worry about, and want, in any framing they like (journey, persona, scenario, pain), plus the raw material behind it — FAQs, sales or support records, win/loss reasons, GSC/PPC/site-search data. This one is **must have**. Prefer queries that are newly appearing, already exposed but underperforming, or adjacent to existing content yet uncovered by the bank.

**The coverage skeleton is enumerated top-down first; signals fill it; attributes are still distilled from signals** (Suda 2026-10-22, adopting Aleyda's step-5 matrix direction). Before collecting, write out the full grid 产品线 × 受众 (the parties in the purchase — a draft list until Workflow step 3 freezes it) × 旅程阶段（八段） from the business scope, so a dimension the collection never reaches stays visible as an empty cell instead of silently not existing. Then collect signals into the cells and distil the Attribute Matrix (brand-side and buyer-side classes together) → name Topics → write Prompts. A cell still empty when the matrix settles is closed with an explicit reason (无买家证据 / 低业务优先，留到后续周期 / 超出范围) in the internal handoff — run `python3 scripts/check_matrix_coverage.py <base-spec.json 或题库.json>` to list the open cells. Do not start by filling in an attribute list and treating the signals as confirmation of it, and never write a Prompt for an empty cell just to fill it — the evidence gates still decide what gets a Prompt. **Weights follow the buyer type**: for B2B, first-party material (calls, tickets, win/loss) is the highest-signal source; for consumer brands the inverse holds and public material (reviews, Reddit, prompt data) can nearly carry the analysis on its own. Public sources do double duty — buyers' language and how the web currently describes the brand are the same corpus to AI.

**Customer input is not "less is better" — swap the collection form, do not cut the information.** What shrinks is the customer's filling burden, never the context; cut the context and all that remains is generic `best X` questions. Sort requests into three tiers:

- **Must have:** the target buyer's real intent, differentiators, what the business does not do, which scenarios are easier to win, and which unique assets the client holds.
- **Best to have:** finer buyer wording and scenario detail — the material that makes a Prompt sound natural instead of generic.
- **Collect ourselves:** official-site facts, who the competitors are and where they are strong, who currently owns the category in AI answers, and the category's naming variants.

Depth varies by layer: business boundaries (product, market, ICP, competitors, differentiation) need the client to **confirm**; Attributes and Topics come from interviews; **Prompt generation depends on internal data**. "We draft, the client ticks and deletes" relieves the Topic layer and does **not** relieve the Prompt layer — real buyer language for Prompt wording cannot be dropped, and drafting for the client never makes the intent pass optional.

The client-facing intake is a **fixed frame, not free-form**: "fill in whatever you like" is not a low bar but no bar, and clients freeze or free-associate. The canonical intake spec lives in the project's 《AI 搜索监测问题确认说明》 — follow it, do not re-invent columns. The rule text itself is [after-sales-rules.md](references/after-sales-rules.md); the Feishu copy 《售后生词规则》 was retired on 2026-10-19 and is no longer authoritative. Its settled shape: five client columns `目标客户 | 客户问题与场景 | 客户原话 | 客户旅程 | 业务重要程度` (the scenario folds into 客户问题与场景; a 限制条件 column was tried and removed), importance on one ordered P-scale as defined there, which already contains frequency — never add a separate frequency column, and never use a middle P as an "undecided" placeholder. The attribute table carries its **own** P1–P3 with different semantics (P1 = decides candidate-set entry); the two scales must not be mixed. Two rules keep the intake honest: **the client gives facts and we make the judgements** (never ask them why they lose deals, how buyers would describe the advantage, or which advantages buyers credit), but do not over-relieve either — frequency, priority, and constraints are their daily sales judgement and stay with them; and **原话 is best-effort**, since most clients cannot produce quotes — a blank cell never blocks intake, it only drops that row to hypothesis grade and triggers our own verification (review mining, community language) before it can back a formal Prompt; never invent quotes to fill it. A client-facing confirmation document is written in Chinese, carries conclusions and answerable open items only, drops question numbering, and leaves our intermediate process to the internal archive file. **Every table in it carries a 客户确认 column, and its convention is write-what-to-change** — the client writes only in the rows needing a correction, deletion, or addition, and leaves every other cell blank; a blank column is a reviewed column, not an unanswered one. When producing the actual customer-facing 属性池 or 主题确认件, use [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md): brand facts first, then the attribute pool, then candidate monitoring questions only when needed; use `品牌方`, not `贵司`.

Keep the original customer wording or a faithful summary as evidence. Separate:

- **observed customer intent**: supported by customer, sales, support, GSC, or monitoring evidence;
- **AI-answer opportunity**: a useful monitoring hypothesis derived from observed intent;
- **brand-advantage hypothesis**: a capability that still needs product or client confirmation.

Do not call a Prompt “high frequency” when it is only a plausible LLM expansion.

### Attribute means buyer decision focus

In after-sales work, an Attribute is not limited to a product feature or
technical parameter. It is the buyer decision focus being monitored under a
Topic and may be a capability, use case, customer pain, audience constraint,
procurement requirement, supply or service risk, or applicability boundary.
Product features become Prompts only when they matter in a real buyer context.

**The class list spans both sides of the table** — brand side (Category,
Feature, Differentiator, Integration, Trust & Security) and buyer side
(Industry & Vertical, Buyer Persona / ICP, Pain Point, Use Case, Evaluation
Criteria, Geography & Market, Constraint). Do not narrow it into a supply-side
capability inventory: ICP, persona, pain and use case are Attribute classes in
their own right, and this is where the apparent "attribute vs customer intent"
duplication usually comes from.

**Customer intent is a separate object, not a third Attribute class.**
Attributes decide **which perception to optimise**; intents decide **in which
user question to fight for that perception**. Keep both passes — attribute pass
first, intent pass second, cross-map third; do not jump straight to the joint
table, and do not merge the two into one column. What collapses into one table
is the **deliverable**: each input pass stays light (for attributes: the
twelve-class sweep from the rule document §3, covering product/service, ICP, differentiators,
and the capabilities buyers most need to verify; for intents: the
journey-organised signal pass from Customer and Market Signals), and the
client sees and confirms a single joint table because two heavyweight standalone
tables are unreadable and unfillable for them. The cross-map in Step 4 is that final
working artifact.

Topic and Prompt both grow out of Attributes, so they are derived and ranked **before** Topics and Prompts are named, in four steps.

**Step 1 — sweep the twelve categories as a gap check.** Sweep Category / Industry & Vertical / Buyer Persona / Pain Point / Use Case / Evaluation Criteria / Differentiator / Feature / Integration / Constraint / Geography & Market / Trust & Security to find what is missing. Never fill them mechanically and never treat the skeleton as a fixed list. The attributes that actually decide the choice are the category-specific ones the skeleton cannot supply — in B2B, Evaluation Criteria, Integration, and Trust & Security are exactly the classes general knowledge cannot fill.

**Step 2 — collect the category-specific attributes from three sources.**

| Source | What to take | Who |
|---|---|---|
| The client's own procurement standard | RFP / tender scorecards received, the evaluation items sales gets asked about most. B2B procurement already scores by domain, so this is the most accurate first-hand source. | Client provides |
| Competitor comparison and feature pages | Competitors have already summarised the category's evaluation dimensions for the market. | We research |
| Already-collected AI answers | Cluster the attribute words AI uses when describing brands in this category to get "the attribute set AI is actually using". Only we can do this layer, and it is the cheapest. | Ours alone |

**Step 3 — B2B and B2C are not one attribute set.** The required categories, the attribute wording, and the data lines all differ; mixing them yields a set that fits nobody. The same holds between different ICPs inside one B2B case: apply the ICP rule in [shared principles](../shared/prompt-generation-principles.md) (「目标企业画像决定一整组决策点」) before deriving attributes.

| Aspect | B2B | B2C |
|---|---|---|
| Skeleton classes seen as required | Industry & Vertical (required); Buyer Persona written as decision / usage / payment / risk-control roles; Evaluation Criteria; Integration; Trust & Security | Industry & Vertical left empty; Buyer Persona as audience traits; Use Case; Pain Point; Evaluation Criteria |
| How attributes are worded | Procurement and risk terms: SLA, compliance certification, integration, total cost of ownership, implementation and migration | Consumption and experience terms: experience, ingredients or materials, price and value, word of mouth and repurchase |
| Data line | Procurement RFP / tender scorecards, sales and CRM records, support tickets, win/loss reasons | Product reviews and purchase enquiries, return reasons, community and social discussion, search terms |
| When one set is acceptable | Only when enterprise and individual buyers are both core and their criteria, scenarios, and competitors substantially overlap. Otherwise split into two cases with separate attributes and separate Prompt sets — never mixed into one. | Same |

**Step 4 — cross-map intents × attributes and record where the P1 Attributes land.** Organise the demand side by the eight journey stages used across the client Base — `发现` / `解决问题` / `评估` / `对比` / `替代方案` / `验证` / `交易` / `购后支持` (2026-10-15; replaces the five-stage 了解需求/比较方案/评估是否适合/准备购买/使用与续费 set, see client-facing-attribute-pool.md → *旅程阶段* for the mapping). Then map each intent to the attribute(s) that can answer it. Not every combination becomes a Query: keep the cells carrying P1 and P2 Attributes (prioritised by importance × changeability, current gap added after the baseline; see [after-sales-rules.md](references/after-sales-rules.md) → *Priority is set in two passes*). An intent with no attribute behind it is low priority; an attribute no intent reaches is self-indulgent differentiation. Do not ask the customer to rank. Topics are clustered from where the P1 Attributes land, and the deliverable is one working table: **journey → intent → linked attribute(s) → Topic → Query → priority** — not a separate attribute table plus a separate intent table.

**Boundaries for this section.**

- Attributes are not kept as a separate library, and no attribute requires its own Topic. Generation-time attributes (which design and explain the Prompts) stay apart from post-analysis attributes clustered out of AI answers: the two can be linked but never share one meaning.
- **Differentiators are Attributes** — one row each in the decision-attribute table with their own priority, never a separate section, never a Topic, never a Tag. The "competitor cannot copy this" test decides **how a claim may be worded as a differentiator**, not whether the dimension earns a row: shared category requirements (compliance certification, integration, SLA) are perfectly good Attributes and often decide the shortlist, they just must not be sold as differentiators. A claim every major competitor can match — global inventory or price advantage, 24/7 multilingual support, "more advanced technology" — is worded as the survivable part instead (not "全球 Content 最丰富" but "针对中国和亚太差旅，把全球内容与亚洲本地资源统一到一个平台") or recorded as parity. Trade-press or self-declared claims are labelled **品牌自述**, never asserted as fact, and gated on client confirmation.
- **Two blocks, not one.** Client-facing attribute sections separate a **品牌事实** table (brand, domain, business model, category, ICP, target customer, geography, applicable boundary — factual, unranked) from a **决策属性** table (ranked, with a client-confirmation column). The same split applies to the final deliverable: the master table's reference shape is `优先级 | 品牌属性 | 客户问题与场景 | Topic | Query | Query 类型 | 选择理由`, with 品牌事实 kept as a separate upfront table. Attribute evidence lives inside 选择理由 — do not add a separate 属性说明与证据 column, and drop any column that would carry the same information twice; the shape is a reference, not a validation checklist. Column naming (Prompt vs Query) is free as long as one document uses one term consistently. The one hard rule: keep 品牌属性 and 客户问题与场景 as adjacent but **never merged** columns — the whole act of translation lives between them, and merging them silently asserts "attribute = intent".
- **P3 attributes stay in the table but get no Prompts.** Keeping them visible lets the client disagree; writing Prompts for them wastes the budget. Only P1/P2 attributes carry Prompts — check this explicitly before delivery. The 选择理由 column carries **answer-layer evidence only** ("competitors are negatively mentioned on this theme at 33%, we are at zero"), never subjective reasoning, so it cannot be talked around by "the client says this matters". A paraphrased row we cannot source is tagged **待验证** rather than quietly kept.
- **The `相对竞品` verdict is researched, not requested.** It records the attribute's **real position in the industry** (领先 / 持平 / 劣势) — not whether it happens to be published. Every P1, and every P2 that carries Prompts, is judged by comparing our position against that product line's leaders — the answer layer first, then the competitors' own public pages (spec sheets, certification pages, service terms), then third-party material. **Where the public layer cannot settle the comparison — typically the brand's own spec or internal capability — ask the client, who knows where its own number sits in the industry; never infer `持平` from the mere fact that neither side published.** **Where the engagement already has collected answers, read the comparison set off the answer layer** — whichever brands actually lead that product line's discovery answers — rather than carrying over a frozen list. The presales competitor-research skill exists for the **pre-data** case, before anything has been collected; once data exists it is superseded. The set differs by **product line × market**: rank each line's brands by mentions in the unbranded discovery answers **of that market** and take the top three per cell; never reuse one line's leaders for another line, or one market's leaders for another market (local champions often outrank the global names). This applies to after-sales only; the presales Case keeps its single frozen set. This is **not** `automatic competitor discovery` — the set is given, and making the comparison is ours. Reserve `待确认` for what the public layer genuinely cannot settle *after* that pass and the client has not yet answered, and name the material that would settle it. Split every verdict into **evidence gap** (capability exists but is unpublished — the fix is a page) versus **capability gap** (capability is absent — the fix is investment); that split is what makes the column actionable — and note it is a *different* axis from the verdict, since a 领先 or 持平 row can sit on either. **A column that returns mostly `待确认` is a research gap, not a finding.**
- Attribute names must be legible to the client in their own industry vocabulary — if the client says "内容源覆盖是什么意思，看不懂", the name is wrong (the industry term was 库存, not 内容); rename it rather than explaining it.
- We draft the attribute list by category; the client only adds, deletes, and corrects, never fills from zero. A dimension the client did not raise but the procurement RFP plainly evaluates (integration, compliance certification, and the like) is raised by us for the client to confirm as fact. In a client-facing table, express such a row as whether it is a **selection gate** — never register certificate numbers or negative lists.
- Interview angles, if used, run When / Where / While / with What / Why / how-feeling / with-Whom, converging on the 5–8 attributes that genuinely affect the choice.

Before adding a new Prompt, require all three:

1. **Evidence:** it is supported by an observed query, answer gap, customer
   language, confirmed business change, or a clearly marked hypothesis source.
2. **Buyer reality:** a recognizable buyer, user, caregiver, service provider,
   or procurement role could naturally ask it.
3. **Incremental decision value:** it changes the candidate set, comparison
   dimension, preference, risk, or applicability judgment.

If any gate fails, keep the idea as a research/evidence-gap note, Tag, or
future hypothesis instead of adding a monitoring Prompt. Do not add a Prompt
just because a Topic has fewer rows than another Topic.

## Search-Demand Anchoring

Use traditional Search Demand to validate that a parent business need exists, not to copy SEO keywords into AI monitoring.

Apply this mapping:

`Search Demand -> parent Topic -> ICP / journey -> attributes and USP -> natural AI Discovery Query`

- Search Demand anchors parent Topics such as `Corporate Travel Management`, `TMC Selection`, `Travel Platform`, or `Travel Cost Management`.
- Product USPs such as APAC coverage, China content, rail, local service, corporate rates, policy, payment, or integration are usually attributes, scenarios, or constraints under a parent Topic.
- Do not create a standalone Topic from a feature or sales phrase unless buyers independently ask for that capability and it has enough distinct Prompts.
- Search-volume figures from different tools, countries, or databases are directional evidence only. Do not present them as comparable exact demand or as AI-answer volume.
- A long-tail regional or ICP Query may be valuable even when the exact keyword has little traditional volume, because it inherits demand from the parent Topic and can create a stronger brand-recommendation context.

## Workflow

0. **Confirm the monitoring scope.** Inherit the presales Case and confirmation record — and, when presales left a 「售前分级参考（内部）」 Base, continue in that Base: its 买家原话, 品牌事实核查 and attribute grades are the public half of the research already done, so add the client-supplied data and split attribute rows into slices instead of re-collecting public sources (re-collect only for a product line or market the presales round did not cover). Then correct changed business priorities and factual boundaries with the customer, and mark outstanding assumptions. Check the scope against the business questions in [representative-library.md](references/representative-library.md) → *Start From Business Questions* — especially the conversion path the visibility should feed and whether audiences ask with different terms or alternatives — and record only what the Case does not already answer. A pending V1 can inform candidates but cannot enter the formal trial until the scope is confirmed. Keep this confirmation distinct from final Prompt approval after trial.
1. **Classify the change.** Decide whether this is a new Topic, a new Prompt under an existing Topic, a revision, a semantic merge, or retirement. Preserve the old Prompt IDs and evidence when modifying an existing set.
2. **Rank evidence.** Prefer, in order: observed monitoring gaps and repeated answer language; GSC/SEO queries; AI answers revealing new attributes or decision standards; confirmed product/market/USP/audience changes; industry changes. Record source and confidence for every new Prompt. **Query fan-out from baseline runs is a lead, not a source**: the terms AI adds on its own (absent from the Prompt wording) may point to a missing Attribute or a new candidate Prompt, but they are hypothesis grade until a real buyer signal (search data, reviews, community, sales records) backs them — follow the 补题用法 rules in [gap-cause-action-table.md](../geo-monitoring/references/gap-cause-action-table.md) → *Query fan-out*. The same holds for every other model-generated suggestion — Perplexity related questions, an LLM listing buyer concerns, persona brainstorming; see [signal-sources.md](references/signal-sources.md) → *每类信源能用来干什么* and *用大模型做意图调研*.
3. **Segment the audience before ranking attributes.** Write the parties in the purchase (who decides, uses, pays, owns, carries the constraint), cut them only where the cut changes eligibility, the dominant criteria or the answer, validate the list against first-party sources, and freeze it before Prompts are written (Suda 2026-10-20; Hbrand went seven → five because citizens and PRs, buyers and renters, were split without a test). Then rank the frozen audiences: each non-base audience is a 买家角色 row in 属性池, only its 重要性 judged (from the business goal and the brand party's 优先 marks; no 相对竞品 or 可改变性), and that 重要性 caps every slice of the audience (中 → P2 at most, 低 → P3; Suda 2026-10-23). See [after-sales-rules.md](references/after-sales-rules.md) → *Audience Segments*.

4. **Anchor parent demand before naming Topics.** Identify the parent Search Demand and customer journey stage first. Then decide whether the proposed Topic is a durable business need or only an attribute/USP cluster. **Prioritise Attributes by importance × changeability before naming anything, and cluster Topics from where the P1s land** (see [after-sales-rules.md](references/after-sales-rules.md) → *Topic and Attribute Selection Criteria*). A direction where a competitor's advantage rests on brand awareness or broad media consensus scores low on changeability and is unlikely to move inside the window, **so do not open a Topic for it** — read the category position from the presales round instead of paying every cycle for a number that cannot change; still give each high-importance Attribute there one candidate Prompt inside the core category Topic, and re-judge after the formal baseline. **Judge this per Attribute, not per Topic**: dropping a Topic must not drop its fixable Attributes with it — re-home each one, and record why for any you leave unmeasured.
5. **Design stable Topics.** The recommended first-stage shape is one category observation Topic plus two same-product buying-scenario Topics; use two Topics when product scope or evidence is genuinely narrow. This is guidance, not a quota. A Topic is a business opportunity worth observing independently over time, not a long sentence or one feature. Use short, scannable names, normally 1–4 English words. Put scenario and attributes in Prompts and Tags, not in the Topic name. A formal Topic needs at least five independent Prompts; if candidate evidence cannot support five, merge it, retain it as a Tag, or report the evidence gap rather than inventing filler. **Record the clustering before Prompts are written**: each `config.topics` entry carries `covered_attributes` (the attribute_plan rows whose P1/P2 landing opened this Topic) and `planned_prompts`, and every Prompt's `topic` must come from these entries — the validator warns when the clustering fields are missing and fails when a `covered_attributes` name is absent from `attribute_plan` or a P1 attribute is homed in no Topic without a reason, so "Topic first" stays checkable instead of the Topic shape being read back off whatever Prompts got written. **A broad Topic must be resolved into its facets**: name the distinct buyer needs it contains — a label like `APAC coverage` may hide coverage breadth, cross-market itineraries, local content and low-cost carriers, local-language service, and multi-supplier data consolidation — and mark which facet each Prompt serves. Without that, one Topic name with N Prompts reads as coverage while every facet actually holds a single Prompt.
6. **Allocate Prompts by incremental value.** Candidate Topic count is not limited — open as many as the evidence supports. Every candidate or formal Topic needs at least five independent Prompts; counts do not need to be equal and there is no permanent after-sales total cap. Explain library size by independent decisions across priority product lines, buyers, markets, journey tasks, constraints and competitor/substitute sets; do not multiply every dimension. Start with the smallest set that covers the Topic's important buying situations and decision focuses. Stop when the meaningful decision coverage is complete. Put the weight on the facet where the brand's advantage meets buyer demand **and the business value sits — the 业务目标 rows, the 业务范围 priority mark on 主要受众 and the 转化路径 row (the priority path; confirmed by the brand party) decide which audiences' slices get the count, not evidence volume alone**; a non-priority audience's slice may carry 目标题数 blank with the cell closed as 低业务优先. Do not spread Prompts evenly across facets for visual balance. Do not create a Prompt merely by changing “best” to “top”, reordering words, or balancing Topic counts.
7. **Choose one prompt type per Prompt.**
   - The `prompt_type` field decides the downstream analysis contract and is the client Base 提示词库 提示词类型 column: `Discovery` (发现), `Competitor` (对比), `Evaluation` (评价), `Verification` (验证), `Accuracy` (准确性), `Category Awareness` (品类认知), `Information` (信息), or `Alternatives` (替代) — the six presales prompt types plus the two after-sales-only additions Information and Alternatives. The prompt type alone decides which statistic a Prompt feeds — see after-sales-rules.md → *Prompt Priorities*. Tags never change routing.
   - Discovery: natural non-branded candidate questions; core visibility opportunity. Goes into the trial; once selected, into the formal baseline.
   - Information: a buyer's own policy, process, cost, rights or dispute question that AI answers with advice, not a candidate list (Suda 2026-10-19). `analysis_type: visibility`, `formal_visibility_eligible: false`. **Read for citation only — whether the answer cites the brand's site; its mention rate is not read** (Suda 2026-10-23, matching shared/canonical-intent-mapping.md). In the formal baseline report every selected Prompt, Information and named-brand ones included, appears with no split by intent (Suda 2026-10-20); for Information only the citation figures are interpreted. The formal-set mention-rate KPI still counts Discovery only, and `formal_visibility_eligible` stays `false` — the field governs the formal stage only. Needs real demand evidence, niche audiences included; whether the brand already has content on it does not decide inclusion. Only questions whose answer leaves a next step the brand's product serves enter the bank; pure-knowledge ones, or ones whose next step is a bank, lawyer or government body, are not written as Prompts (record them in `config.parked` with the reason). It belongs to the `experimental` layer (Suda 2026-10-20): it runs in the trial, it stays out of the formal set by default (the brand party may still buy it into the formal set; it then runs every period but never enters the mention-rate KPI), and otherwise it is re-run only on a trigger (content published for it, a policy change, a quarterly review); one whose formal-baseline runs show no brand citation stops. See after-sales-rules.md → *Prompt Priorities*.
   - Evaluation: a concrete attribute, use case, or decision standard; experimental layer — useful for sentiment matrix and brand-perception diagnosis, but does not feed the visibility KPI (mention rate is the only delivered metric). Runs in the trial; once selected, in the formal baseline, then re-run only on a trigger. When the brand's own name ranks among its top search queries (GSC / GA4), a few brand-named Evaluation and Verification Prompts (is it legit, is it good for X, does it offer Y) go into the bank in the monitoring layer so the 评估 and 验证 stages are covered; they run in the trial (and the formal baseline once selected) and never count toward mention rate (Hbrand 2026-10-19).
   - Competitor (客户标签 对比, 2026-10-23 从「竞品对比」简化; 10-22 从「竞品」改出): one-to-one comparison only when a new competitor, region, dimension, USP, or material gap justifies it. The target brand is always one side; never compare two competitors without the brand. **Must carry a concrete use case — `constraints` non-empty (output-contract gate 38); without one AI answers "it depends"**. Read for win/loss (reported with and without ties) and sentiment.
   - Alternatives (客户标签 替代, after-sales only, split out of Competitor 2026-10-22): alternatives to a named competitor, where the brand can appear in the answer list. Read as 提及率 within the alternatives list (how many of the 5 runs list the brand, and where; Suda 2026-10-23 — the former name 列入率 meant the same count) plus sentiment, reported on its own line; whether it counts toward the mention-rate KPI is undecided (Suda 2026-10-23): banks default to `formal_visibility_eligible: false` until it is settled, and the validator accepts either value; 列入≠推荐. Non-branded alternatives questions stay Discovery. Same layer and cadence as Competitor; pre-2026-10-22 banks keep these typed Competitor, no migration.
   - Category Awareness: one or two per product line asking how to choose; experimental layer — not in visibility, not in the formal set. Goes through the trial while the attribute pool is being judged, to understand AI's buying criteria and calibrate the attribute matrix; results are used as reference, not as a recurring monitored metric.
   - Verification: experimental layer — asks whether AI recognises that the brand holds a specific capability; the failure it catches is that AI does not know the brand has it. Primary trigger: Discovery shows low visibility on the corresponding attribute. Read a capability Verification Prompt against the Discovery Prompts on the same attribute (trust gap vs comprehension gap, see after-sales-rules.md → *Prompt Priorities*). Not in the trial batch, except the brand-named checks backed by brand-search demand (see Evaluation above).
   - Accuracy: experimental layer — asks whether a specific brand fact (price, spec, feature, integration, policy, certification) that AI can already state is right; the failure it catches is that AI states it wrongly. Not in the trial batch; data-driven trigger only (the client identifies a wrong AI claim and confirms the correct answer with an official source). One fact per Prompt; no Accuracy Prompt without a confirmed official source. Verification and Accuracy are distinct intents: Verification covers a capability AI does not recognise, Accuracy a fact AI gets wrong — a Prompt sits on one or the other, never both. Accuracy errors are found during attribute-pool research, not by Prompts: for each factual P1 (and factual P2 carrying Prompts) check public-layer consistency and what the answer layer actually states, and record findings in the row for client confirmation. Only rows where a wrong answer changes the purchase, the discovery answers cannot show the fact (or already state it wrongly/outdatedly), and the client has confirmed the right answer with an official source become Accuracy Prompts — typically two to five per market. See after-sales-rules.md → *Topic and Attribute Selection Criteria*.
   - For the first staged set, use Discovery plus any demand-backed Information Prompts: draft the Discovery group
     first, then add the other intents as the situation requires, each for its
     own evidence-backed purpose — never to satisfy a role quota or fill a slot.
   - **Discovery dominates: at least 50% of a bank** (Suda 2026-10-23 — most
     clients buy on mention rate, and only Discovery feeds it). Two ratios are
     kept apart. *The full research bank* (candidate set across Topics) uses
     this reference mix: 发现 50% / 对比 15% / 品类认知 10% / 评价 10% / 信息 5%
     / 替代 5% / 验证 5% (Aleyda and Peec direction, our own numbers — no
     industry standard exists). B2B SaaS and high-trust categories may raise
     对比 / 评价 / 验证; standardised ecommerce may raise 发现. *The committed
     formal set* is the core Discovery Prompts whose mention rate is the KPI;
     named-brand Evaluation and Verification never enter that denominator,
     since they would inflate it. The mix is a coverage reference, not a quota:
     never pad Discovery to reach 50% at the cost of real buyer demand (a
     leader-default category such as Hbrand sits below it on purpose —
     record why), and never add a type to fill its share. Validator gate 40
     warns below 50%. Category Awareness is a low-frequency top-up; Accuracy is
     not part of routine expansion and needs a fact-check purpose plus complete
     official sources.
8. **Keep fields separate.** Every Prompt must have `topic`, `region`, and `prompt_type`. `tags` is **optional**: leave it empty unless a tag carries something the other fields do not. Never repeat `topic`, `region`, or `prompt_type` in Tags, and do not spend a tag on organisation those columns already express. A useful tag is a name a reader cannot derive from elsewhere: an attribute, a buyer role, or a use case. **Keep each tag as short as the value allows** — the bare name, no field prefix and no qualifier. When inheriting presales v8 rows, explicitly normalize the `Prompt Type:` and `Brand Scope:` tags into the after-sales fields; do not reject the inherited bank merely because it uses the older tag shape.
   - **Review the market, then decide reuse.** Build the lightweight internal coverage pass before writing or inheriting individual Prompts: product line, audience, journey stage, market/language, buyer constraint, competitor/alternative set and business priority, plus local terminology, source ecosystem, regulation, currency, trust, availability and service expectations when relevant. Only reuse a candidate intent and `intent_key` when local evidence supports equivalent buyer decisions and expected answer sets. Otherwise mark it `localized`, `market_specific`, or `not_supported`, and adapt, add, or omit the market Prompt with evidence. Translate and adapt approved wording to the market's language; same-language markets may reuse identical wording only after this review. Materialize and version a separate Prompt-set snapshot for each market/language so each has its own baseline; the client Base, by contrast, holds all markets of the engagement in one copy split by its 市场 field, with 提示词矩阵 slices shared across markets; in 提示词库 a Prompt is one row per language — markets sharing intent and language share the row, different languages get their own rows, paired only by `intent_key` in the bank JSON (client-facing-attribute-pool.md → *Several markets in one Base*). **Platform does not affect Prompt generation**: each market's set runs across its platforms unchanged. Never average market baselines or silently merge a market delta into another market's historical series. Show the filled slices to the brand party in the client Base's 提示词矩阵 table — one row per buyer situation × attribute, linked to 属性池 (where 重要性, 相对竞品, 可改变性 and 还缺什么 are judged once per attribute), carrying a formula priority (we draft, they review for missing buyer situations and wrong judgements); keep the evidence notes behind reuse decisions in the internal handoff.
9. **Write buyer language.** The query must sound like a target buyer asking an AI, contain one main decision, avoid leading the answer, and include enough category context to prevent cross-category answers. Take the wording from buyer-language sources (AI prompt samples, first-party records, reviews, communities); every condition the Prompt adds beyond its attribute must be in the 约束 of a quote it cites, and is listed in the Prompt's `constraints` (output-contract gate 36); the official site, competitor pages, client interviews or drafts, and keyword tools decide what to cover, never how a Prompt is worded. A search query becomes a Prompt only through the rewrite rules in [signal-sources.md](references/signal-sources.md) → *搜索词改写成题面*. Discovery Prompts must naturally ask for providers, platforms, or solutions to consider, choose, or recommend. Pure methodology, trend, education, or “how can I improve...” questions do not count as core Discovery unless the project explicitly wants a problem-awareness track; such a Prompt is written as Information when it carries real buyer demand (otherwise left out), and the validator fails any English Discovery Prompt that counts for visibility yet asks for no candidates. Write policy and rule questions neutrally — never presuppose the rule in the wording, because rules change (Singapore removed the 15-month wait for some private-property owners in 2026-07 while two LLM research reports still stated it). For a category whose leader is the default, write the underlying need rather than "which platform" (see after-sales-rules.md → *When the leader is the default*). Do not rewrite a working “Which …” Prompt only to sound more personal — it narrows the answer's brand list without moving target mention (see after-sales-rules.md → *Discovery Quality*). **A Prompt under a non-base audience must show who is asking — stated or implied**: most already imply it through what they ask (「HDB resale flat」 → citizen or PR buyer); add the audience in its own words (「with three cats」「as a foreigner」) only where a generic buyer could ask the same question, since AI then answers for the generic buyer and the audience reading is empty. The audience is not a 约束 and is not listed in `constraints`. Verification, Accuracy and the per-Topic low-condition anchor are exempt; an implied identity the term list cannot catch records `audience_implicit` with the reason (after-sales-rules.md → *Audience Segments* Step 6; validator gate 39 reads `config.audience_terms`).
10. **Validate Discovery quality.** Every Discovery Prompt must:
   - omit the target brand, frozen competitors, and other brand names;
   - expose a recognizable category and a commercial selection task;
   - test one primary buyer intent;
   - use no condition, one simple condition, or a meaningful compound condition that changes the candidate set;
   - avoid redundant containment questions such as “global coverage and APAC coverage” or “China and Asia” when one term already contains the other;
   - preserve at least one natural low-condition Prompt per Topic — it anchors the Topic's category visibility against the constrained Prompts (the validator warns per Topic when `constraint_type` is recorded and no low-condition Discovery Prompt exists); the one deliberate exemption is a leader-default category (after-sales-rules.md → *When the leader is the default*), recorded as `config.leader_default` with the reason;
   - pass the evidence, buyer-reality, and incremental-decision gates above.
   - **Natural visibility is computed from Discovery Prompts only.** Named-brand Competitor, Evaluation, and Accuracy results are read on their own; they never enter the natural-discovery statistic.
   - When several brands must be evaluated, keep one identical wording across them. Compounds such as "customer support" as a Discovery sub-type stay Discovery — a specific attribute does not by itself make a Prompt an Evaluation.
11. **Deduplicate semantically.** Compare the new query with the whole active set. The unit of dedup is the **purchase decision**, not the wording: merge two Prompts that resolve the same decision (same candidate set, same comparison dimension, same condition that changes the answer) however differently they read. Normalised text uniqueness only catches synonym and word-order rewrites, so near-equivalent phrasings must be merged on human review. Keep both only when they change the buyer, region, use case, decision stage, competitor dimension, or expected answer set. **A pair differing only by the category's name is a deliberate variant, not a duplicate** — register the naming variants in `config.category_aliases` and the validator exempts such pairs (synonymous category phrasings measure 25–50 pp apart; Profound, adopted 2026-10-22). **A capability phrasing and an outcome phrasing of the same need (「带 Slack 集成的工具」 vs 「出现故事机会时提醒团队的工具」) count as a meaningful pair when they pull different candidate sets; when they pull the same set, keep the outcome phrasing — buyers speak in outcomes** (Aleyda variant table, adopted 2026-10-22). A changed condition counts only when a cited quote's 约束 carries it: a scenery variant (parked on the street, a minivan, freezing weather) with no evidence is the same decision reworded, and the validator groups it with its base Prompt (output-contract gate 37). The 2026-10-22 harness A/B found this the most common defect, in every set from both harnesses.
12. **Trial** (Suda 2026-10-23; the candidate baseline — 全候选 × 全平台 × 5 次 — is retired). Run every candidate Prompt 3 times on each monitored platform, each in a fresh session, 5 at most per platform; Competitor, Category Awareness and Accuracy Prompts go through the same trial while the attribute pool is being judged. Judge per platform: two or three runs failing the same way means reword or cull; one failure or disagreeing runs adds two runs on that platform (reword only at three of five, otherwise keep and mark 高波动); a failure on one platform only is reworded if the wording causes it, otherwise that platform is excluded for the Prompt with the reason. Read only for intent/category misreads, answer-task fit per prompt type, segment reach, same-answer pairs and run-to-run consistency. Fill each Discovery and Alternatives Prompt's 信源壁垒 (待判 / 来源追不上 / 无) from the answers. The readings are shown to the brand party as context and never enter a statistic; **brand mention is never a verdict**, and **whether a direction can be moved is the changeability condition**, not a reason to remove a valid zero-mention Prompt (after-sales-rules.md → *Stage 3*).
13. **Rank and deliver the Base.** Rank candidates by the slice tier (重要性 × 可改变性, capped by the audience), dropping one tier only for 信源壁垒 = 来源追不上; within a tier 领先 goes before 持平 and nothing else orders it — trial readings never do (after-sales-rules.md → *Stage 4*). Formal slots fill by prompt type: Discovery (at least half), then Alternatives, then Competitor, then the rest; prompt type never lowers a tier. **Where a P1 attribute's Discovery Prompts read low at the trial, recommend one Verification Prompt on that same attribute** — its answer splits the gap into 知道但不推荐 vs 不知道该能力 (Profound ch3, adopted 2026-10-22; after-sales-rules.md → *Prompt Priorities*). Once the client Base is visible to the brand party, IDs are frozen and changes are deployed incrementally only — no delete-and-rebuild, record_ids must survive; run `python3 scripts/diff_base_against_spec.py --base <token> --spec <spec.json>` before and after each deploy and call it done only at zero differences (client-facing-attribute-pool.md → *IDs freeze*). Run the deterministic checks in [output-contract.md](references/output-contract.md) — the validator fails on brand or competitor names in Discovery and on queries not written in the collection language, and warns on keyword-shaped, multi-question, over-long, wrong-currency and near-duplicate wording, and checks that every Prompt carries `journey_stage` / `audience` / `group_role` / `attribute_ref` / `evidence_refs` under those names (gates 8, 12, 33, 34; older field names are read as aliases, conflicting values fail), warns when the evidence spans fewer than three source families or a collected buyer quote backs no Prompt (gates 34, 35), fails a Prompt carrying a condition no cited quote's 约束 backs and warns when one purchase decision is asked twice (gates 36, 37; the bank carries `config.buyer_quotes` and each Prompt its `constraints`, see output-contract.md → *Conditions and the buyer-quote table*), and once Prompts carry `review_status` it counts only 已批准 Prompts as covering an attribute; settle every warning before delivery — then perform a semantic review for evidence traceability, Topic fit, no cross-topic competitor use, no invented facts, no duplicates, useful incremental value, and clear lifecycle/lineage status. **Reconcile the intent pass against the Prompt set in both directions** — every P1/P2 intent carried by at least one Prompt, every Prompt's intent present as a row in the client's intent table — and make the master table's intent column quote the intent table verbatim so the two cannot drift. Before delivery, review the internal market coverage pass and confirm every retained market-specific delta has evidence and every omitted slice has a reason; distinguish official competitors from substitutes and the status quo without changing the frozen list. For each Prompt group state the diagnostic business question, possible action, role and next review trigger. Then check the evidence layer itself: does a sentiment matrix for this category actually exist, and did it cover the discovery questions?
14. **Select, lock, hand over.** The brand party picks at most 10 Prompts per purchased Topic among 已批准 ones, **never by a Prompt's own reading**. At lock, selected Prompts move to 状态 正式 and every other candidate to 停测; save the immutable version and lock the assessment scope — KPI Prompts, platforms × markets × languages and runs, denominator, calculation (after-sales-rules.md → *Assessment scope lock*). Hand both to `geo-monitoring` for the **formal baseline** (30 runs per query × platform × country × language; whether the 30 span days is decided per engagement) and periodic collection; cadence, re-run triggers, seasonality and versioning live in `geo-monitoring` → 采集频率与重跑 / 正式基线与版本. **A formal Prompt's wording is immutable**: to reword one, set the old Prompt 停测 and open a new question_id in a new set version — never edit the text in place (after-sales-rules.md → *Maintenance*). Review the formal set once, 2–4 weeks after periodic monitoring starts, before optimisation content goes live where possible.
15. **Optimization directions are monitoring's output.** Once formal-baseline readings exist, `geo-monitoring` locates gaps and hands directions to the content team (gap-cause-action table), in the optimisation order computed in the baseline report (baseline-report.md → *优化顺序*). Selection never emits that note from Case research alone.

## Topic and Prompt Sizing

The recommended first-stage shape is **one category observation Topic + two
same-product buying-scenario Topics** (two Topics can be justified), with
variable counts based on evidence-backed decision coverage. A customer-confirmed,
locked, or formal Topic requires at least five independent Prompts and
**at most 10 per purchased Topic** — the formal set is the deliverable; the
candidate set may be larger. Ten or more genuinely distinct important intents
is a split signal, acted on at formal-set selection when the brand party
cannot pick its 10 without dropping intents it needs — not a candidate-stage
cap and not a pre-quote auto-split (after-sales-rules.md → *When to
split a Topic*); candidate Prompt counts carry no upper bound. Weight the counts rather than equalising
them — put the weight on the buying-scenario Topics the brand can win and leave
the category observation Topic lighter. **For one market × one product line the bank may total 30–60 Prompts across the three layers, of which the core layer needs only 20–30** (Suda 2026-10-23; core = the non-branded Discovery Prompts that run every period, see representative-library.md → *Roles and Refresh*): go beyond 30 core only to cover a P1 slice that would otherwise have no Prompt, and say which. The experimental and monitoring layers make up the rest. Candidate Topics below five remain
explicitly pending merge, Tag treatment, or evidence completion. **Before concluding a Topic is short, re-check attribution**: a Prompt filed under the wrong Topic is a common cause of one Topic falling under the floor while another quietly carries a Prompt that does not serve it. Move it to where its actual purchase decision belongs, then count again — that is a correction, not padding. Do not add a
Prompt to fill a visual gap, or turn the presales `<=60` discovery-stage limit
into a permanent after-sales library cap.

## Output

Unless the user requests another format, deliver:

- A customer-facing attribute pool / confirmation document when the task involves scope confirmation, attribute priority, Topic approval, or Prompt wording approval. Follow [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md): brand facts first, then 属性池, then candidate monitoring questions when needed; every table has a `客户确认` column using the write-what-to-change convention.
- A machine-readable JSON monitoring set.
- An upload CSV carrying the five required columns `query,question_zh,topic,region,prompt_type`, plus `tags` and/or `cadence` only when the receiving pipeline wants them; add no other columns.
- A cadence/schedule file.
- An input/evidence diff listing why each Topic or Prompt was added, changed, merged, or retained.
- In that same internal diff, a compact market-coverage section: reviewed slices, local evidence, retained/omitted intent decisions and reasons. Its filled slices are the client Base's 提示词矩阵 table, linked to the 属性池 table where each attribute is judged once; do not build a second customer-facing matrix.
- A short validation summary that opens with the validator's readiness line (Not ready / Usable / Ready, see the verdict note after output-contract gate 37), plus known incompatibilities when an older presales validator enforces fixed quotas. List the unused buyer quotes the validator reports, each with its decision.

For a single-product update such as Bbrand N1, keep the new product line isolated from unrelated product Topics. Reuse frozen Case boundaries, but do not carry unrelated competitors into the new Topic.
