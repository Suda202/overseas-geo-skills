# GEO Prompt Selection Builder（选词）

## Purpose

选词决定测哪些题：售前选词工具（调研 → 属性池 → 提示词矩阵与行优先级 → 从矩阵聚出候选主题 → 确认件 → 候选题集），读试跑结果（各监测平台 × 3 次）排序、由客户选正式题并锁版本，以及签约后根据监测结果和业务变化补充、合并、淘汰 Prompt。跑基线、按期采集、出报告归 `geo-monitoring`（2026-10-22 拆出）。2026-10-22 起由「售后生词」改名为「选词」：这套方法早已前移给售前选词工具用，只叫售后已名不副实。它也是写题规则的唯一来源，`geo-presales-prompt-builder`（前置售前诊断）的写题规则与门禁引用本 skill。目标是发现新的可优化机会和细分分析视角，而不是把覆盖面机械做满。

Use this skill when the user asks to research and select a GEO Prompt set for a new client, or to create, revise, expand, prune, organize, or schedule a monitoring Prompt set. Read [after-sales-rules.md](references/after-sales-rules.md) before designing Topics or Prompt quotas. Read [representative-library.md](references/representative-library.md) when the task involves market/language coverage, attribute-pool gap checking, Prompt groups, localization, or sampling protocol. Read [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md) when producing or updating the client confirmation Base (使用说明 + 业务范围 / 品牌事实核查 / 买家原话 / 属性池 / 提示词矩阵 / 提示词库 / 需要品牌方提供的数据; competitors are 竞品（n） rows in 业务范围), an 属性池 or 对客确认件, or any customer-facing handoff. Read [output-contract.md](references/output-contract.md) when producing JSON, CSV, cadence, or audit artifacts. Two method-mapping references: [aleyda-21-step-mapping.md](references/aleyda-21-step-mapping.md) tracks coverage against Aleyda's 21 steps, [peec-geobubbles-ahrefs-mapping.md](references/peec-geobubbles-ahrefs-mapping.md) maps Peec / GeoBubbles / Ahrefs concepts to ours; consult them when auditing method coverage or translating an external methodology's term.

## Operating Boundary

- **Selection and monitoring:** start from existing data, real queries, AI answers, business changes, and content opportunities; preserve valuable existing Prompts and explain additions/removals.
- **Early presales diagnosis:** use `geo-presales-prompt-builder` for the one-off diagnosis bank (public evidence only, no confirmation Base, at most 60 Prompts). It follows this skill's writing rules; only its stage differences live there.
- **Out of scope:** defining metric calibers (owned by `geo-presales-report-editor` core) or sentiment rules (owned by `geo-presales-sentiment-judge`), crawler collection, baselines and reports (all in `geo-monitoring`), written report conclusions, and competitor discovery or freezing. This skill hands monitoring the Prompt set and collection plan; it reads the readings back to select and maintain Prompts.
- A frozen competitor list may be consumed for comparison Prompts, but this skill must not silently select, replace, or verify competitors.

## Required Inputs

Accept the inputs available in the current task; do not invent a parallel business schema.

- Existing monitoring Prompt set and its Topics, if available.
- Brand/product Case and the official domain.
- At least one real signal: existing monitoring results, GSC/SEO query data, AI-answer gaps, sales/customer language, customer-review language, CRM/customer-success findings, a new product/market/USP/audience, or an industry change.
- Region and language for the monitoring run.
- The business goal for this service period and the marketing campaigns inside it (业务目标 / 营销活动 rows in the client Base 业务范围, Suda 2026-10-23). They decide where the Prompt count goes and rank the audiences; they are never buyer evidence and never license a Prompt by themselves (client-facing-attribute-pool.md → *Settled table set*).
- Frozen competitors and their Topic boundaries when competitor Prompts are requested.
- Reusable researched context and a customer-confirmation document, when
  available; otherwise create a staged handoff artifact before formal lock.

Presales may leave the researched Case as a pending-confirmation V1. Before the
trial, the customer must confirm the current business priority,
product/buyer/market scope, and factual and exclusion boundaries. This is
separate from approving the formal Prompt set after the trial and ranking; record both
decisions. If presales confirmation already exists, review changes rather than
asking the customer to start over.

If the user only provides a product brief with no after-sales signal, build a
clearly labelled first hypothesis set and list the evidence that still needs
confirmation. It may support Discovery/Diagnostic exploration, but is not
formal-baseline-ready. Do not present LLM-invented expansions as high-frequency
demand.

## Customer and Market Signals

After-sales Prompt work should start from **signal collection**, not from a product feature list and not from a finished attribute list. Signals are what we gather; the Attribute Matrix is what we distil out of them. Before attributes and their importance are settled, collect user language from all four sources — **search data, sales records, reviews, and community** — reusing what already exists and filling whichever is missing. The client supplies the data only the brand party can access — sales and CRM records, support tickets and chat logs (asked first — a summarised version from the brand party is enough), plus Search Console and Bing Webmaster Tools (required: read-only access, the longest available history; non-branded question and long queries, plus the whole Bing AI Performance report), the Google Ads Search Terms report when the brand runs search ads, site and help-centre search, AI referral traffic from GA4 (last 12 months), and its own testimonials (if available). Ask only for data that changes a Prompt-generation judgement, and word the client list as 必须接入 (Search Console and Bing Webmaster Tools only) / 优先提供 / 有就提供, never 必须给 — the dropped items are listed in signal-sources.md → 客户提供什么; we collect search data (non-branded demand, PAA and related searches, keyword tools), reviews (product and competitor reviews), and community language (Reddit, forums, industry communities). Strip names, emails, phone numbers, account IDs and customer company names from client records before turning them into buyer language, follow the brand party's privacy and data-use rules, and keep raw records internal — never in the bank or the handoff. Which sites to use depends on the industry and the market, and the full client-data list is in the same file — see [signal-sources.md](references/signal-sources.md). Before collecting from a site, look up which channel reaches it (direct fetch, headless render, proxy, DataForSEO, or none) in [community-channels.md](references/community-channels.md). Every P1 / P2 needs at least one source; a row with none is marked hypothesis grade. Signals to gather:

- sales and CRM language, including why customers bought, did not buy, switched, renewed, or churned;
- customer-support and customer-success questions, misunderstandings, adoption barriers, and recurring service concerns;
- customer-review and public-discussion language;
- GSC/SEO queries as demand clues, never as Prompts copied without interpretation;
- customer role, business scenario, decision stage, constraints, and the decision or risk the question is trying to resolve.

The customer must supply a **signal pass** of their own: based on their sales, support, win/loss, and churn records, what their target buyers actually ask, worry about, and want, in any framing they like (journey, persona, scenario, pain), plus the raw material behind it — FAQs, sales or support records, win/loss reasons, GSC/PPC/site-search data. This one is **must have**. Prefer queries that are newly appearing, already exposed but underperforming, or adjacent to existing content yet uncovered by the bank.

**The coverage skeleton is enumerated top-down first; signals fill it; attributes are still distilled from signals** (Suda 2026-10-22, adopting Aleyda's step-5 matrix direction). Before collecting, write out the full grid 产品线 × 受众 (the parties in the purchase — a draft list until Workflow step 3 freezes it) × 旅程阶段（八段） from the business scope, so a dimension the collection never reaches stays visible as an empty cell instead of silently not existing. Then collect signals into the cells and distil the Attribute Matrix (brand-side and buyer-side classes together) → name Topics → write Prompts. A cell still empty when the matrix settles is closed with an explicit reason (无买家证据 / 低业务优先，留到后续周期 / 超出范围) in the internal handoff — run `python3 scripts/check_matrix_coverage.py <base-spec.json 或题库.json>` to list the open cells. Do not start by filling in an attribute list and treating the signals as confirmation of it, and never write a Prompt for an empty cell just to fill it — the evidence gates still decide what gets a Prompt. **Weights follow the buyer type**: for B2B, first-party material (calls, tickets, win/loss) is the highest-signal source; for consumer brands the inverse holds and public material (reviews, Reddit, prompt data) can nearly carry the analysis on its own. Public sources do double duty — buyers' language and how the web currently describes the brand are the same corpus to AI.

**Customer input is not "less is better" — swap the collection form, do not cut the information.** What shrinks is the customer's filling burden, never the context; cut the context and all that remains is generic `best X` questions. Sort requests into three tiers:

- **Must have:** the target buyer's real intent, differentiators, what the business does not do, which scenarios are easier to win, and which unique assets the client holds.
- **Best to have:** finer buyer wording and scenario detail — the material that makes a Prompt sound natural instead of generic.
- **Collect ourselves:** official-site facts, who the competitors are and where they are strong, who currently owns the category in AI answers, and the category's naming variants.

Depth varies by layer: business boundaries (product, market, ICP, competitors, differentiation) need the client to **confirm**; Attributes and Topics come from interviews; **Prompt generation depends on internal data**. "We draft, the client ticks and deletes" relieves the Topic layer and does **not** relieve the Prompt layer — real buyer language for Prompt wording cannot be dropped, and drafting for the client never makes the intent pass optional.

The client-facing intake is a **fixed frame, not free-form**: "fill in whatever you like" is not a low bar but no bar, and clients freeze or free-associate. The canonical intake spec lives in the project's 《AI 搜索监测问题确认说明》 — follow it, do not re-invent columns. The rule text itself is [after-sales-rules.md](references/after-sales-rules.md); the Feishu copy 《售后生词规则》 was retired on 2026-10-19 and is no longer authoritative. Its settled shape: five client columns `目标客户 | 客户问题与场景 | 客户原话 | 客户旅程 | 业务重要程度` (the scenario folds into 客户问题与场景; a 限制条件 column was tried and removed), importance on one ordered P-scale as defined there, which already contains frequency — never add a separate frequency column, and never use a middle P as an "undecided" placeholder. The matrix carries its **own** P1–P3 with different semantics (row priority = business focus × buyer-evidence strength, Suda 2026-10-28); the two scales must not be mixed. Two rules keep the intake honest: **the client gives facts and we make the judgements** (never ask them why they lose deals, how buyers would describe the advantage, or which advantages buyers credit), but do not over-relieve either — frequency, priority, and constraints are their daily sales judgement and stay with them; and **原话 is best-effort**, since most clients cannot produce quotes — a blank cell never blocks intake, it only drops that row to hypothesis grade and triggers our own verification (review mining, community language) before it can back a formal Prompt; never invent quotes to fill it. A client-facing confirmation document is written in Chinese, carries conclusions and answerable open items only, drops question numbering, and leaves our intermediate process to the internal archive file. **In the Base the brand party edits cells directly and there is no 客户确认 column; a document-format piece carries one, and its convention is write-what-to-change** — the client writes only in the rows needing a correction, deletion, or addition, and leaves every other cell blank; a blank column is a reviewed column, not an unanswered one. When producing the actual customer-facing confirmation piece, use [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md): brand facts first, then the attribute pool, then candidate monitoring questions only when needed; use `品牌方`, not `贵司`.

Keep the original customer wording or a faithful summary as evidence. Separate:

- **observed customer intent**: supported by customer, sales, support, GSC, or monitoring evidence;
- **AI-answer opportunity**: a useful monitoring hypothesis derived from observed intent;
- **brand-advantage hypothesis**: a capability that still needs product or client confirmation.

Do not call a Prompt “high frequency” when it is only a plausible LLM expansion.

### Attribute means a buyer-relevant point the brand wants to own

An Attribute is a point the brand wants AI to associate with it **and** buyers actually use when choosing (Profound AEO Guide ch2: "The specific, buyer-relevant things you want your brand to be known for in AI answers"). It may be a capability, use case, customer pain, procurement requirement, supply or service risk, or applicability boundary. Collect both sides — brand side (Category, Feature, Differentiator, Integration, Trust & Security) and buyer side (Industry & Vertical, Pain Point, Use Case, Evaluation Criteria, Geography & Market, Constraint, and what buyers weigh at the transaction and after purchase) — and keep what buyers actually use. Product features become Attributes only when they matter in a real buyer context. Concrete values (「under $300」「three cats」) are not Attributes: they live in Prompts, taken from buyer quotes.

**The pool judges one thing, 相对竞品** (Suda 2026-10-28). How much an attribute matters depends on the buying situation, so it is judged on the matrix row that lists it; whether content can move AI's answer is judged per Prompt from the trial's cited domains. 属性池 carries no 优先级, 重要性 or 可改变性, no audience rows and no row standing in for no-condition category Prompts.

**Customer intent is a separate object, not a third Attribute class.** Attributes decide **which perception to optimise**; the matrix row decides **in which buyer situation to fight for it**; the Prompt is the question. Keep the passes apart — attributes, then the matrix (situations × the attributes that matter there), then Topics clustered from the matrix, then Prompts — and do not merge attribute and situation into one column. The brand party reads the result in 提示词库, whose 出题原因 carries the chain.

Attributes are gathered before the matrix is drawn, in four steps.

**Step 1 — sweep the twelve categories as a gap check.** Sweep Category / Industry & Vertical / Buyer Persona / Pain Point / Use Case / Evaluation Criteria / Differentiator / Feature / Integration / Constraint / Geography & Market / Trust & Security to find what is missing. Never fill them mechanically and never treat the skeleton as a fixed list. The attributes that actually decide the choice are the category-specific ones the skeleton cannot supply — in B2B, Evaluation Criteria, Integration, and Trust & Security are exactly the classes general knowledge cannot fill.

**Step 2 — collect the category-specific attributes from three sources.**

| Source | What to take | Who |
|---|---|---|
| The client's own procurement standard | RFP / tender scorecards received, the evaluation items sales gets asked about most. B2B procurement already scores by domain, so this is the most accurate first-hand source. | Client provides |
| Competitor comparison and feature pages | Competitors have already summarised the category's evaluation dimensions for the market. | We research |
| Already-collected AI answers and the research pre-run | Cluster the attribute words AI uses when describing brands in this category to get "the attribute set AI is actually using". Only we can do this layer, and it is the cheapest. | Ours alone |

**Research pre-run — crawl first, then research** (Suda 2026-10-29). Before the public research and before 相对竞品 is judged, collect what AI says today about the category and the brands, then research to fill and check it. Per product line × market language, write a CSV with a `query` column holding: one Category Awareness Prompt asking how to choose (`What should I look for when choosing [category]?`); and one report-wording Evaluation Prompt for the brand and for each 竞品 row in 业务范围 for that line and market (`Evaluate the [category] company [brand]`, the same wording for every brand), all in the market language. Keep that wording; do not switch to or add pros and cons (Suda 2026-10-29): in an brand-o Kenya test (4 brands × 4 platforms × 1 run) both wordings listed weaknesses in all 16 answers, and the Evaluate wording returned more citations (9.8 vs 7.1 per answer), named more other brands (4.7 vs 2.6) and carried the risk records (counterfeit, after-sales, warranty) that pros and cons mostly missed, whose weaknesses read the same across brands (`10-售前诊断报告/评测数据/brand-o/售前/_trial/prerun-wording-20261029/结论.md`). Run it once on each platform the engagement will monitor with `geo-presales-report-builder/scripts/collect_answers.py --questions <csv> --out <dir> --regions <market>` (one run per cell is the collector's default; 1 + 4 brands on 4 platforms is about 20 calls). Read the answers as leads, never as verdicts: buying criteria the pool lacks, each brand's strengths and weaknesses as AI states them, regulator, recall and complaint records, brand facts AI states wrongly, and the pages AI cites. Then research: open the cited pages and the official layer, and fill what the answers did not reach. A criterion becomes an attribute, a strength or weakness a 相对竞品 basis, and a wrong fact a 品牌事实核查 row only after it is checked; 判据与证据 cites the pre-run answer and the page that confirmed it. One run per platform is enough because nothing here is a statistic. Asking a model directly does not replace it: the monitored platforms answer from web retrieval and cite their sources, which is what the research follows. These Prompts are research, not monitoring — they never enter the bank or 提示词库, the trial, the formal set or any baseline — and the pre-run is repeated only when a product line or market is added, the competitor set changes, or the category's buying standard visibly shifts. The buyer-wording Evaluation Prompts in the bank are a separate thing: they need a use case from a matrix row and are written after the matrix.

**Step 3 — B2B and B2C are not one attribute set.** The required categories, the attribute wording, and the data lines all differ; mixing them yields a set that fits nobody. The same holds between different ICPs inside one B2B case: apply the ICP rule in [shared principles](../shared/prompt-generation-principles.md) (「目标企业画像决定一整组决策点」) before deriving attributes.

| Aspect | B2B | B2C |
|---|---|---|
| Skeleton classes seen as required | Industry & Vertical (required); Buyer Persona written as decision / usage / payment / risk-control roles; Evaluation Criteria; Integration; Trust & Security | Industry & Vertical left empty; Buyer Persona as audience traits; Use Case; Pain Point; Evaluation Criteria |
| How attributes are worded | Procurement and risk terms: SLA, compliance certification, integration, total cost of ownership, implementation and migration | Consumption and experience terms: experience, ingredients or materials, price and value, word of mouth and repurchase |
| Data line | Procurement RFP / tender scorecards, sales and CRM records, support tickets, win/loss reasons | Product reviews and purchase enquiries, return reasons, community and social discussion, search terms |
| When one set is acceptable | Only when enterprise and individual buyers are both core and their criteria, scenarios, and competitors substantially overlap. Otherwise split into two cases with separate attributes and separate Prompt sets — never mixed into one. | Same |

**Step 4 — sweep the journey stages and judge 相对竞品.** Check each of the eight stages — `发现` / `解决问题` / `评估` / `对比` / `替代方案` / `验证` / `交易` / `购后支持` (client-facing-attribute-pool.md → *旅程阶段*) — for an attribute buyers weigh there that the pool still misses; transaction and post-purchase are the usual holes (Nbrand had almost none). Then judge each attribute's 相对竞品 with its basis line (client-facing-attribute-pool.md → *属性池*). 劣势 attributes are never listed on matrix rows; 待确认 ones are, and their rows cap at P2. Do not ask the customer to rank.

**Boundaries for this section.**

- Each attribute is kept once, in 属性池, and no attribute requires its own Topic. Generation-time attributes (which design and explain the Prompts) stay apart from post-analysis attributes clustered out of AI answers: the two can be linked but never share one meaning.
- **Differentiators are Attributes** — one row each in 属性池, never a separate section, never a Topic, never a Tag. The "competitor cannot copy this" test decides **how a claim may be worded as a differentiator**, not whether the dimension earns a row: shared category requirements (compliance certification, integration, SLA) are perfectly good Attributes and often decide the shortlist, they just must not be sold as differentiators. A claim every major competitor can match — global inventory or price advantage, 24/7 multilingual support, "more advanced technology" — is worded as the survivable part instead (not "全球 Content 最丰富" but "针对中国和亚太差旅，把全球内容与亚洲本地资源统一到一个平台") or recorded as parity. Trade-press or self-declared claims are labelled **品牌自述**, never asserted as fact, and gated on client confirmation.
- **Two blocks, not one.** Client-facing attribute sections separate a **品牌事实** table (brand, domain, business model, category, ICP, target customer, geography, applicable boundary — factual, unranked) from a **决策属性** table (in the Base this is 属性池, edited in place; not ranked — priority lives on matrix rows). The same split applies to the final deliverable: the master table's reference shape is `优先级 | 品牌属性 | 客户问题与场景 | Topic | Query | Query 类型 | 选择理由`, with 品牌事实 kept as a separate upfront table. Attribute evidence lives inside 选择理由 — do not add a separate 属性说明与证据 column, and drop any column that would carry the same information twice; the shape is a reference, not a validation checklist. Column naming (Prompt vs Query) is free as long as one document uses one term consistently. The one hard rule: keep 品牌属性 and 客户问题与场景 as adjacent but **never merged** columns — the whole act of translation lives between them, and merging them silently asserts "attribute = intent".
- **P3 matrix rows stay but get no Prompts.** Keeping them visible lets the client disagree; writing Prompts for them wastes the budget. Only P1/P2 rows carry Prompts — check this explicitly before delivery. The 选择理由 column carries **answer-layer evidence only** ("competitors are negatively mentioned on this theme at 33%, we are at zero"), never subjective reasoning, so it cannot be talked around by "the client says this matters". A paraphrased row we cannot source is tagged **待验证** rather than quietly kept.
- **The `相对竞品` verdict is researched, not requested.** It records the attribute's **real position in the industry** (优势 / 持平 / 劣势) — not whether it happens to be published. Every attribute listed on a matrix row is judged by comparing our position against that product line's leaders — the answer layer first, then the competitors' own public pages (spec sheets, certification pages, service terms), then third-party material. **Where the public layer cannot settle the comparison — typically the brand's own spec or internal capability — ask the client, who knows where its own number sits in the industry; never infer `持平` from the mere fact that neither side published.** **Where the engagement already has collected answers, read the comparison set off the answer layer** — whichever brands actually lead that product line's discovery answers — rather than carrying over a frozen list. The presales competitor-research skill exists for the **pre-data** case, before anything has been collected; once data exists it is superseded. The set differs by **product line × market**: rank each line's brands by mentions in the unbranded discovery answers **of that market** and take the top three per cell; never reuse one line's leaders for another line, or one market's leaders for another market (local champions often outrank the global names). This applies to after-sales only; the presales Case keeps its single frozen set. This is **not** `automatic competitor discovery` — the set is given, and making the comparison is ours. Reserve `待确认` for what the public layer genuinely cannot settle *after* that pass and the client has not yet answered, and name the material that would settle it. Split every verdict into **evidence gap** (capability exists but is unpublished — the fix is a page) versus **capability gap** (capability is absent — the fix is investment); that split is what makes the column actionable — and note it is a *different* axis from the verdict, since an 优势 or 持平 row can sit on either. **A column that returns mostly `待确认` is a research gap, not a finding.** 劣势 attributes are never listed on matrix rows (Suda 2026-10-28) — content cannot move what the brand lacks — so check for a remedy channel (foundation year, bridging course, quota) before judging 劣势: public layer first, then the brand party.
- Attribute names must be legible to the client in their own industry vocabulary — if the client says "内容源覆盖是什么意思，看不懂", the name is wrong (the industry term was 库存, not 内容); rename it rather than explaining it.
- We draft the attribute list by category; the client only adds, deletes, and corrects, never fills from zero. A dimension the client did not raise but the procurement RFP plainly evaluates (integration, compliance certification, and the like) is raised by us for the client to confirm as fact. In a client-facing table, express such a row as whether it is a **selection gate** — never register certificate numbers or negative lists.
- Interview angles, if used, run When / Where / While / with What / Why / how-feeling / with-Whom, converging on the 5–8 attributes that genuinely affect the choice.

Before adding a new Prompt, require all three:

1. **Evidence:** it is supported by an observed query, answer gap, customer
   language, confirmed business change, or a clearly marked hypothesis source.
2. **Buyer reality:** a recognizable buyer, user, caregiver, service provider,
   or procurement role could naturally ask it.
3. **Incremental decision value:** it changes the candidate set, comparison
   dimension, preference, risk, or applicability judgment.

If any gate fails, keep the idea as a research/evidence-gap note, Tag, or
future hypothesis instead of adding a monitoring Prompt. Do not add a Prompt
just because a Topic has fewer rows than another Topic.

## Search-Demand Anchoring

Use traditional Search Demand to validate that a parent business need exists, not to copy SEO keywords into AI monitoring.

Apply this mapping:

`Search Demand -> parent Topic -> ICP / journey -> attributes and USP -> natural AI Discovery Query`

- Search Demand anchors parent Topics such as `Corporate Travel Management`, `TMC Selection`, `Travel Platform`, or `Travel Cost Management`.
- Product USPs such as APAC coverage, China content, rail, local service, corporate rates, policy, payment, or integration are usually attributes, scenarios, or constraints under a parent Topic.
- Do not create a standalone Topic from a feature or sales phrase unless buyers independently ask for that capability and it has enough distinct Prompts.
- Search-volume figures from different tools, countries, or databases are directional evidence only. Do not present them as comparable exact demand or as AI-answer volume.
- A long-tail regional or ICP Query may be valuable even when the exact keyword has little traditional volume, because it inherits demand from the parent Topic and can create a stronger brand-recommendation context.

## Workflow

0. **Confirm the monitoring scope.** Inherit the presales Case and confirmation record — and, when presales left a 「售前分级参考（内部）」 Base, continue in that Base: its 买家原话, 品牌事实核查 and attribute grades are the public half of the research already done, so add the client-supplied data and build the matrix rows instead of re-collecting public sources (re-collect only for a product line or market the presales round did not cover). Then correct changed business priorities and factual boundaries with the customer, and mark outstanding assumptions. Check the scope against the business questions in [representative-library.md](references/representative-library.md) → *Start From Business Questions* — especially whether audiences ask with different terms or alternatives — and record only what the Case does not already answer. A pending V1 can inform candidates but cannot enter the formal trial until the scope is confirmed. Keep this confirmation distinct from final Prompt approval after trial. For a new product line or market, run the research pre-run next — crawl first, then research (*Attribute means…* → Research pre-run).
1. **Classify the change.** Decide whether this is a new Topic, a new Prompt under an existing Topic, a revision, a semantic merge, or retirement. Preserve the old Prompt IDs and evidence when modifying an existing set.
2. **Rank evidence.** Prefer, in order: observed monitoring gaps and repeated answer language; GSC/SEO queries; AI answers revealing new attributes or decision standards; confirmed product/market/USP/audience changes; industry changes. Record source and confidence for every new Prompt. **Query fan-out from baseline runs is a lead, not a source**: the terms AI adds on its own (absent from the Prompt wording) may point to a missing Attribute or a new candidate Prompt, but they are hypothesis grade until a real buyer signal (search data, reviews, community, sales records) backs them — follow the 补题用法 rules in [gap-cause-action-table.md](../geo-monitoring/references/gap-cause-action-table.md) → *Query fan-out*. The same holds for every other model-generated suggestion — Perplexity related questions, an LLM listing buyer concerns, persona brainstorming; see [signal-sources.md](references/signal-sources.md) → *每类信源能用来干什么* and *用大模型做意图调研*.
3. **Segment the audience before building the matrix.** Write the parties in the purchase (who decides, uses, pays, owns, carries the constraint), cut them only where the cut changes eligibility, the dominant criteria or the answer — a group that only follows a Topic (wallet questions are asked by wallet holders) is not a cut — validate the list against first-party sources, and freeze it before Prompts are written (Suda 2026-10-20; Hbrand went seven → five because citizens and PRs, buyers and renters, were split without a test). Mark the priority audiences in 业务范围 (主要受众（优先）, or named by a 业务目标); that mark feeds matrix-row priority in step 4. There are no audience rows in 属性池 (Suda 2026-10-28). See [after-sales-rules.md](references/after-sales-rules.md) → *Audience Segments*.

4. **Draw the matrix skeleton and judge row priority.** Write out 产品线 × 受众 × 市场 × 旅程阶段 from 业务范围, top-down (Suda 2026-10-22), open only the cells worth testing — never the full Cartesian product — and close the rest with a reason in the internal handoff (`scripts/check_matrix_coverage.py` lists open cells). On each open row, list from 属性池 the attributes that matter in that situation — those buyers there use to drop or seriously compare options; listing is the per-situation importance judgement. A no-condition category row exists only when the brand party asks for the head term; its 属性关联 stays empty. Then judge each row's priority, **the only place priority is judged** (Suda 2026-10-28): business focus × buyer-evidence strength, with the journey-stage cap and the 待确认 cap, basis written in 优先级依据 (client-facing-attribute-pool.md → *提示词矩阵*; after-sales-rules.md → *Priority*). P3 rows get no Prompts this period. A direction that is only a feature or sales phrase does not earn a row of its own (*Search-Demand Anchoring*).
5. **Cluster Topics from the matrix rows.** A Topic is a set of intents around one shared buyer need or purchase decision, each represented by a Prompt; it is the unit of statistics, competitor comparison, optimisation diagnosis and purchase. Once rows are prioritised, cluster the P1 and P2 rows by the decision task — rows whose buyers solve the same problem or make the same decision, with the same competitor set, evaluation standard and optimisation direction, form one Topic (Suda 2026-10-28). We cluster by judgement, never by text similarity (algorithmic keyword clustering drifts with its threshold and fragments one need; 30-选Topic与生词/研究与方法/SEO主题聚类方向调研-20261027.md). P1 rows are a Topic's core; P2 rows join a related Topic or get no Prompts this period; a P1 row that fits no Topic opens its own. File each row under one Topic, splitting a row that serves two. Name the Topic in the buyer's words for the category or task, from demand evidence (parent search term, buyer quotes); short names, normally 1–4 English words in the bank, Chinese in the Base. There is no coverage / depth Topic type and no fixed first-stage shape. Before Prompts are written, check: every P1 row is homed; every Topic holds a P1 row, or a 业务目标 / 核心可见度问题 names it; each Topic's planned Prompts (the sum of its rows' 目标题数) reach five; the three split tests pass (after-sales-rules.md → *When to split a Topic*). Set the recommended order (business-focus rows first, then P1 count; after the trial, a high share of 可改变性 低 moves a Topic back). Record it in the Base 主题 table (client-facing-attribute-pool.md → *主题表*) and in the bank: `config.slices` carries each row with its `topic_id`, and each `config.topics` entry its `source_slices` and `planned_prompts`, so the clustering stays checkable instead of being read back off whatever Prompts got written. **A broad Topic must be resolved into its facets**: name the distinct buyer needs it contains and mark which facet each Prompt serves; one Topic name with N Prompts otherwise reads as coverage while every facet holds a single Prompt.
6. **Allocate Prompts by decision need.** 目标题数 on each row = the number of clearly different decision needs in that situation — decision difference, not phrasing count (Suda 2026-10-28): blank for a row outside this period, 1 for one independent decision, 2 or more only when the needs would change the candidate list (a different attribute on the row, or a value of one attribute — two cats vs four or more). Pick the values from the row's attributes' buyer-quote 约束 and name each need in 备注. Candidate Topic count is not limited; every candidate or formal Topic needs at least five independent Prompts; there is no permanent after-sales total cap. Self-check: the P1 rows' 目标题数 should roughly match the formal slots (at most 10 per purchased Topic). Do not spread Prompts evenly for visual balance, and do not create a Prompt merely by changing "best" to "top", reordering words, or balancing Topic counts.
7. **Choose one prompt type per Prompt.**
   - The `prompt_type` field decides the downstream analysis contract and is the client Base 提示词库 提示词类型 column: `Discovery` (发现), `Competitor` (对比), `Evaluation` (评价), `Verification` (验证), `Accuracy` (准确性), `Category Awareness` (品类认知), `Information` (问题解决), or `Alternatives` (替代) — the six presales prompt types plus the two after-sales-only additions Information and Alternatives. The prompt type alone decides which statistic a Prompt feeds — see after-sales-rules.md → *Prompt Priorities*. Tags never change routing.
   - Discovery: natural non-branded candidate questions; core visibility opportunity. Goes into the trial; once selected, into the formal baseline.
   - Information (问题解决): a buyer asking how to solve a problem or reach a goal, which AI answers with advice, not a candidate list (Suda 2026-10-19; client label renamed from 信息 and scope narrowed to problem-solving on 2026-10-26). **Not written by default** (Suda 2026-10-29): it reads only whether the brand's pages are cited, which is not the KPI, and before the brand has content for the problem the reading is almost always zero. Write it in the first round only when the brand party's 业务目标 or 核心可见度问题 names that problem-solving need; it then runs in the trial as below. Otherwise write it after the formal baseline, when the content plan targets that problem: run it once before the content goes live and once after, as a diagnostic outside the formal set and the KPI. Pure knowledge questions — policy, rules, cost, rights or disputes asked for their own sake — are not this type. `analysis_type: citation` (shared/canonical-intent-mapping.md), `formal_visibility_eligible: false`. **Read for citation only — whether the answer cites the brand's site; its mention rate is not read** (Suda 2026-10-23, matching shared/canonical-intent-mapping.md). In the formal baseline report every selected Prompt, Information and named-brand ones included, appears with no split by intent (Suda 2026-10-20); for Information only the citation figures are interpreted. The formal-set mention-rate KPI still counts Discovery only, and `formal_visibility_eligible` stays `false` — the field governs the formal stage only. Needs real demand evidence, niche audiences included; whether the brand already has content on it does not decide inclusion. Only a problem whose solution runs through what the brand serves enters the bank — the brand's product, tool or official content is a fitting citation; one the answer settles with general advice, or whose next step is a bank, lawyer or government body, is not written as a Prompt (record it in `config.parked` with the reason). Not a dumping ground for everything that does not fit elsewhere: a question whose answer would appropriately be a candidate list stays Discovery, and comparison stays Competitor. When written in the first round it belongs to the `experimental` layer (Suda 2026-10-20): it runs in the trial, it stays out of the formal set by default (the brand party may still buy it into the formal set; it is then re-tested monthly but never enters the mention-rate KPI), and otherwise it is re-run only on a trigger (content published for it, a policy change); one whose formal-baseline runs neither cite the brand's domain nor name any platform stops. See after-sales-rules.md → *Prompt Priorities*.
   - Evaluation: a concrete attribute, use case, or decision standard, worded as a buyer asks about the brand (`Is [brand] worth it for [use case]?`; the `Evaluate the …` report wording belongs to the research pre-run and to diagnostics — after-sales-rules.md → *Evaluation wording*, Suda 2026-10-29); experimental layer — useful for sentiment matrix and brand-perception diagnosis, but does not feed the visibility KPI (mention rate is the only delivered metric). Runs in the trial; once selected, in the formal baseline, then re-tested monthly (cadence by prompt type: `geo-monitoring` → 采集频率与重跑, Suda 2026-10-26). When the brand's own name ranks among its top search queries (GSC / GA4), a few brand-named Evaluation Prompts (is it legit, is it good for X) go into the bank in the monitoring layer so the 评估 stage is covered; they run in the trial (and the formal baseline once selected) and never count toward mention rate (Hbrand 2026-10-19; brand-named Verification Prompts are not written this way, Suda 2026-10-27).
   - Competitor (客户标签 对比, 2026-10-23 从「竞品对比」简化; 10-22 从「竞品」改出): one-to-one comparison only when a new competitor, region, dimension, USP, or material gap justifies it. The target brand is always one side; never compare two competitors without the brand. **Must carry a concrete use case — `constraints` non-empty (output-contract gate 38); without one AI answers "it depends"**. Read for win/loss (reported with and without ties) and sentiment. Write one only when the brand party wants that win/loss reading and buyers really weigh the two brands for that use case; re-checking 相对竞品 is not a reason, since the research pre-run already returns AI's appraisal of the brand and each competitor (Suda 2026-10-29).
   - Alternatives (客户标签 替代, after-sales only, split out of Competitor 2026-10-22): alternatives to a named competitor, where the brand can appear in the answer list. Read as 提及率 within the alternatives list (in how many runs the brand is listed, and where; Suda 2026-10-23 — the former name 列入率 meant the same count) plus sentiment, reported on its own line; whether it counts toward the mention-rate KPI is undecided (Suda 2026-10-23): banks default to `formal_visibility_eligible: false` until it is settled, and the validator accepts either value; 列入≠推荐. Non-branded alternatives questions stay Discovery. Same layer and cadence as Competitor; pre-2026-10-22 banks keep these typed Competitor, no migration.
   - Category Awareness: not written into the bank (Suda 2026-10-29). It is the research pre-run before the attribute pool is judged — one per product line and market language, one run per monitored platform (*Attribute means…* → Research pre-run); it is not trialled, not monitored and takes no slot.
   - Verification: a diagnostic, not a monitored Prompt (Suda 2026-10-27) — asks whether AI recognises that the brand holds a specific capability; the failure it catches is that AI does not know the brand has it. Written only after the formal baseline, when an attribute on a P1 row reads low mention in its Discovery Prompts (an attribute on a P2 row whose 相对竞品 is 优势 may get one too; never 待确认; one per attribute). It is not trialled, takes no formal-set slot, stays out of the KPI and sits outside the formal set, so adding it changes neither the set version nor the assessment scope. Read it against the Discovery Prompts on the same attribute (trust gap vs comprehension gap, see after-sales-rules.md → *Prompt Priorities*); after that first reading it is re-run only on an event trigger.
   - Accuracy: a diagnostic, not a monitored Prompt (Suda 2026-10-27) — asks whether a specific brand fact (price, spec, feature, integration, policy, certification) that AI can already state is right; the failure it catches is that AI states it wrongly. Accuracy errors are found by research, not by Prompts: for each factual attribute listed on a P1 or P2 row check public-layer consistency and what the collected answers (presales or trial) state, and record conflicts in 品牌事实核查. A row becomes an Accuracy Prompt only when all three hold: a wrong answer would change shortlisting or purchase; the answers already state it wrongly or outdatedly, or the fact recently changed; and the brand party has confirmed the right answer with an official source page. Most markets need none. It is not trialled (the right answer is confirmed first), takes no formal-set slot and stays out of the KPI; it runs once after the brand party's fix goes live, then only on an event trigger. One fact per Prompt; a Prompt is Verification or Accuracy, never both. See after-sales-rules.md → *Topic and Attribute Selection Criteria*.
   - For the first staged set, use Discovery, plus Information only where the brand party names the need: draft the Discovery group
     first, then add the other intents as the situation requires, each for its
     own evidence-backed purpose — never to satisfy a role quota or fill a slot.
   - **Discovery dominates: at least 50% of a bank** (Suda 2026-10-23 — most
     clients buy on mention rate, and only Discovery feeds it). Two ratios are
     kept apart. *The full research bank* (candidate set across Topics) uses
     this reference mix: 发现 50% / 对比 15% / 评价 10% / 替代 5% / 验证 5%, the
     rest wherever the evidence is (问题解决 only where the brand party names it) (Aleyda and Peec direction, our own numbers — no
     industry standard exists). B2B SaaS and high-trust categories may raise
     对比 / 评价 / 验证; standardised ecommerce may raise 发现. *The committed
     formal set* is the core Discovery Prompts whose mention rate is the KPI;
     named-brand Evaluation and Verification never enter that denominator,
     since they would inflate it. The mix is a coverage reference, not a quota:
     never pad Discovery to reach 50% at the cost of real buyer demand (a
     leader-default category such as Hbrand sits below it on purpose —
     record why), and never add a type to fill its share. Validator gate 40
     warns below 50%. Accuracy is
     not part of routine expansion and needs a fact-check purpose plus complete
     official sources.
8. **Keep fields separate.** Every Prompt must have `topic`, `region`, and `prompt_type`. `tags` is **optional**: leave it empty unless a tag carries something the other fields do not. Never repeat `topic`, `region`, or `prompt_type` in Tags, and do not spend a tag on organisation those columns already express. A useful tag is a name a reader cannot derive from elsewhere: an attribute, a buyer role, or a use case. **Keep each tag as short as the value allows** — the bare name, no field prefix and no qualifier. When inheriting presales v8 rows, explicitly normalize the `Prompt Type:` and `Brand Scope:` tags into the after-sales fields; do not reject the inherited bank merely because it uses the older tag shape.
   - **Review the market, then decide reuse.** Build the lightweight internal coverage pass before writing or inheriting individual Prompts: product line, audience, journey stage, market/language, buyer constraint, competitor/alternative set and business priority, plus local terminology, source ecosystem, regulation, currency, trust, availability and service expectations when relevant. Only reuse a candidate intent and `intent_key` when local evidence supports equivalent buyer decisions and expected answer sets. Otherwise mark it `localized`, `market_specific`, or `not_supported`, and adapt, add, or omit the market Prompt with evidence. Translate and adapt approved wording to the market's language; same-language markets may reuse identical wording only after this review. Materialize and version a separate Prompt-set snapshot for each market/language so each has its own baseline; the client Base, by contrast, holds all markets of the engagement in one copy split by its 市场 field, with 提示词矩阵 slices shared across markets; in 提示词库 a Prompt is one row per language — markets sharing intent and language share the row, different languages get their own rows, paired only by `intent_key` in the bank JSON (client-facing-attribute-pool.md → *Several markets in one Base*). **Platform does not affect Prompt generation**: each market's set runs across its platforms unchanged. Never average market baselines or silently merge a market delta into another market's historical series. The filled situations are the client Base's 提示词矩阵 — one row per Topic × product line × audience × market × stage, listing the attributes that matter there and carrying the row's priority (client-facing-attribute-pool.md → *提示词矩阵*); the brand party may read it but does not have to. Keep the evidence notes behind reuse decisions in the internal handoff.
9. **Write buyer language.** The query must sound like a target buyer asking an AI, contain one main decision, avoid leading the answer, and include enough category context to prevent cross-category answers. Take the category name, conditions and problem words from buyer-language sources (AI prompt samples, first-party records, reviews, communities) and phrase them the way the market's buyers ask — no type has a mandatory sentence form or opening (`Best …`, `Which …`, `What are the best …` all work), only what its wording must do (after-sales-rules.md → *Reference wording per prompt type*, Suda 2026-10-29); every condition the Prompt adds beyond its attribute must be in the 约束 of a quote it cites and belong to an attribute its row lists, and is listed in the Prompt's `constraints` (output-contract gate 36); the official site, competitor pages, client interviews or drafts, and keyword tools decide what to cover, never how a Prompt is worded. A search query becomes a Prompt only through the rewrite rules in [signal-sources.md](references/signal-sources.md) → *搜索词改写成题面*. Discovery Prompts must naturally ask for providers, platforms, or solutions to consider, choose, or recommend. Pure methodology, trend, education, or “how can I improve...” questions do not count as core Discovery unless the project explicitly wants a problem-awareness track; such a Prompt is written as Information when it carries real buyer demand (otherwise left out), and the validator fails any English Discovery Prompt that counts for visibility yet asks for no candidates. Write policy and rule questions neutrally — never presuppose the rule in the wording, because rules change (Singapore removed the 15-month wait for some private-property owners in 2026-07 while two LLM research reports still stated it). For a category whose leader is the default, write the underlying need rather than "which platform" (see after-sales-rules.md → *When the leader is the default*). Do not rewrite a working “Which …” Prompt only to sound more personal — it narrows the answer's brand list without moving target mention (see after-sales-rules.md → *Discovery Quality*). **A Prompt under a non-base audience must show who is asking — stated or implied**: most already imply it through what they ask (「HDB resale flat」 → citizen or PR buyer); add the audience in its own words (「with three cats」「as a foreigner」) only where a generic buyer could ask the same question, since AI then answers for the generic buyer and the audience reading is empty. The audience is not a 约束 and is not listed in `constraints`. Verification, Accuracy and a requested head-term Prompt are exempt; an implied identity the term list cannot catch records `audience_implicit` with the reason (after-sales-rules.md → *Audience Segments* Step 6; validator gate 39 reads `config.audience_terms`).
10. **Validate Discovery quality.** Every Discovery Prompt must:
   - omit the target brand, frozen competitors, and other brand names;
   - expose a recognizable category and a commercial selection task;
   - test one primary buyer intent;
   - carry up to three conditions by default, each with buyer evidence of its own; four or more only after a reality review — a quote stating them together or a written reason the combination is a real, frequent purchase task (after-sales-rules.md → *Compound conditions*); at any count, write the buyer's wording for each need rather than the brand's spec values, and never offer the brand's advantage as the reason a combination is real (advantage decides which needs get Prompts and which go first); a condition that does not change the candidate set in the trial merges back
   - avoid redundant containment questions such as “global coverage and APAC coverage” or “China and Asia” when one term already contains the other;
   - do not write a bare category question by default (Suda 2026-10-29) — 「best wireless earbuds」「best fast charger」, a market name alone not counting as a condition: category leaders own its answers, content rarely moves it, and it would take one of a Topic's ten formal slots. Write one only when the brand party asks for that head term, and say so in 出题原因 (the validator warns on every no-condition Discovery Prompt so the request is checked). Aleyda's step 6 does mix unconstrained prompts in for broad category visibility; we leave them out on purpose;
   - pass the evidence, buyer-reality, and incremental-decision gates above.
   - **Natural visibility is computed from Discovery Prompts only.** Named-brand Competitor, Evaluation, and Accuracy results are read on their own; they never enter the natural-discovery statistic.
   - When several brands must be evaluated, keep one identical wording across them. Compounds such as "customer support" as a Discovery sub-type stay Discovery — a specific attribute does not by itself make a Prompt an Evaluation.
11. **Deduplicate semantically.** Compare the new query with the whole active set. The unit of dedup is the **purchase decision**, not the wording: merge two Prompts that resolve the same decision (same candidate set, same comparison dimension, same condition that changes the answer) however differently they read. Normalised text uniqueness only catches synonym and word-order rewrites, so near-equivalent phrasings must be merged on human review. Keep both only when they change the buyer, region, use case, decision stage, competitor dimension, or expected answer set. **A pair differing only by the category's name is a deliberate variant, not a duplicate** — register the naming variants in `config.category_aliases` and the validator exempts such pairs (synonymous category phrasings measure 25–50 pp apart; Profound, adopted 2026-10-22). **A capability phrasing and an outcome phrasing of the same need (「带 Slack 集成的工具」 vs 「出现故事机会时提醒团队的工具」) count as a meaningful pair when they pull different candidate sets; when they pull the same set, keep the outcome phrasing — buyers speak in outcomes** (Aleyda variant table, adopted 2026-10-22). **When a cluster merges, keep the wording that stands for the most 买家原话 in the cluster; on a tie keep the outcome phrasing; move every merged-away Prompt's quotes onto the kept Prompt's `evidence_refs`** — quote count stands in for Profound's cluster Coverage Score, whose formula is unpublished and which needs search-volume data we do not have (adopted 2026-10-23). A changed condition counts only when a cited quote's 约束 carries it: a scenery variant (parked on the street, a minivan, freezing weather) with no evidence is the same decision reworded, and the validator groups it with its base Prompt (output-contract gate 37). The 2026-10-22 harness A/B found this the most common defect, in every set from both harnesses.
12. **Trial** (Suda 2026-10-23; the candidate baseline — 全候选 × 全平台 × 5 次 — is retired). Run every candidate Prompt 3 times on each monitored platform, each in a fresh session, 5 at most per platform — Discovery, Alternatives, Competitor, Evaluation and Information alike; Verification and Accuracy are not trialled, and Category Awareness is not in the bank (it ran before the pool). Judge per platform: two or three runs failing the same way means reword or cull; one failure or disagreeing runs adds two runs on that platform (reword only at three of five, otherwise keep and mark 高波动); a failure on one platform only is reworded if the wording causes it, otherwise that platform is excluded for the Prompt with the reason. Read only for intent/category misreads, answer-task fit per prompt type, segment reach, same-answer pairs and run-to-run consistency. Fill every trialled Prompt's 可改变性 (高 / 中 / 低) from the top 20 cited domains of its answers — 官网 (brand and competitor official sites, the brand's own pages on its 转化路径 channel) and 社区 (communities the brand party posts in from its own account) against 难影响 (third-party reviews, media, rankings, government, YouTube…); no fixed threshold, whichever tier holds most citations decides (client-facing-attribute-pool.md → *提示词库* → 可改变性; renamed from 信源壁垒 2026-10-28). Mark an initial AI 认知差距 as 试跑初判 where the answers show it. Then do the one write-back pass (相对竞品 re-checked from Competitor and Evaluation answers, wrong brand facts into 品牌事实核查). The readings go to the brand party in a separate trial report marked 供参考、不作统计 and never enter a statistic or the recommendation order; **brand mention is never a verdict**, and **whether a direction can be moved is the 可改变性 reading**, not a reason to remove a valid zero-mention Prompt (after-sales-rules.md → *Stage 3*). When two groups of Prompts in one Topic surface clearly different competitor lists, split the Topic — the one case after writing that moves a Topic.
13. **Rank and deliver the Base.** A Prompt's 优先级 is its matrix row's tier, dropped one tier when its 可改变性 is 低; `scripts/write_prompt_reasons.py` prefills it into 提示词库 (an editable single-select; a hand change needs 「改档：理由，定为 Px」 in 出题原因, Suda 2026-10-28). The brand's own trial reading never moves it (after-sales-rules.md → *Stage 4*). Formal slots fill by tier first; **within a tier** by prompt type — Discovery (at least half), then Alternatives, then Competitor, then Information (问题解决), then the rest — and within one type 优势 before 持平; that is the only ordering inside a tier, and prompt type never crosses tiers. **Publish the three answers the brand party asks for** (Suda 2026-10-23): why this Prompt and why this tier go into 提示词库 出题原因, written per Prompt by script from the row's 优先级依据 and the 可改变性 basis; why this Topic first is the 主题 table's 推荐顺序 and the 按主题 × 优先级 chart (after-sales-rules.md → *Topic recommendation order*). Every judgement carries its written basis before the value is filled — 相对竞品 in 属性池 判据与证据, row priority in 优先级依据; run `python3 scripts/check_client_base.py --base <token>` before sending — it fails a judgement with no basis line and any retired wording left in 使用说明 or field names. Once the client Base is visible to the brand party, IDs are frozen and changes are deployed incrementally only — no delete-and-rebuild, record_ids must survive; run `python3 scripts/diff_base_against_spec.py --base <token> --spec <spec.json>` before and after each deploy and call it done only at zero differences (client-facing-attribute-pool.md → *IDs freeze*). Run the deterministic checks in [output-contract.md](references/output-contract.md) — the validator fails on brand or competitor names in Discovery and on queries not written in the collection language, and warns on keyword-shaped, multi-question, over-long, wrong-currency and near-duplicate wording, and checks that every Prompt carries `journey_stage` / `audience` / `group_role` / `attribute_ref` / `evidence_refs` under those names (gates 8, 12, 33, 34; older field names are read as aliases, conflicting values fail), warns when the evidence spans fewer than three source families or a collected buyer quote backs no Prompt (gates 34, 35), fails a Prompt carrying a condition no cited quote's 约束 backs and warns when one purchase decision is asked twice (gates 36, 37; the bank carries `config.buyer_quotes` and each Prompt its `constraints`, see output-contract.md → *Conditions and the buyer-quote table*), and once Prompts carry `review_status` it counts only 已批准 Prompts as covering an attribute; settle every warning before delivery — then perform a semantic review for evidence traceability, Topic fit, no cross-topic competitor use, no invented facts, no duplicates, useful incremental value, and clear lifecycle/lineage status. **Reconcile the matrix against the Prompt set in both directions** — every P1/P2 row's planned needs carried by Prompts, every Prompt filed on a row. Before delivery, review the internal market coverage pass and confirm every retained market-specific delta has evidence and every omitted slice has a reason; distinguish official competitors from substitutes and the status quo without changing the frozen list. For each Prompt group state the diagnostic business question, possible action, role and next review trigger. Then check the evidence layer itself: does a sentiment matrix for this category actually exist, and did it cover the discovery questions?
14. **Select, lock, hand over.** The brand party picks at most 10 Prompts per purchased Topic among 已批准 ones, **never by a Prompt's own reading**. At lock, selected Prompts move to 状态 正式 and every other candidate is deleted from the Base (ID and reason kept in `config.retired`, bank status 停测 — the Base holds only Prompts under test); save the immutable version and lock the assessment scope — KPI Prompts, platforms × markets × languages and runs, denominator, calculation (after-sales-rules.md → *Assessment scope lock*). Hand both to `geo-monitoring` for the **formal baseline** (30 runs per query × platform × country × language; whether the 30 span days is decided per engagement) and periodic collection; cadence, re-run triggers, seasonality and versioning live in `geo-monitoring` → 采集频率与重跑 / 正式基线与版本. **A formal Prompt's wording is immutable**: to reword one, set the old Prompt 停测 in the bank, delete its Base row, and open a new question_id in a new set version — never edit the text in place (after-sales-rules.md → *Maintenance*). Review the formal set once, 2–4 weeks after periodic monitoring starts, before optimisation content goes live where possible.
15. **Optimization directions are monitoring's output.** Once formal-baseline readings exist, `geo-monitoring` locates gaps and hands directions to the content team (gap-cause-action table), in the optimisation order computed in the baseline report (baseline-report.md → *优化顺序*). Selection never emits that note from Case research alone. **After the formal baseline, add the diagnostics**: one Verification Prompt per attribute on a P1 row whose Discovery Prompts read low — its answer splits the gap into 知道但不推荐 vs 不知道该能力 and so decides on-site vs off-site work (Profound ch3, adopted 2026-10-22) — and an Accuracy Prompt for each fact that passed the three conditions, run once the brand party's fix is live. Neither takes a formal-set slot.

## Topic and Prompt Sizing

Topics come from the matrix (Workflow step 5); there is no fixed first-stage shape and no coverage / depth type, and counts vary with evidence-backed decision coverage. A customer-confirmed,
locked, or formal Topic requires at least five independent Prompts and
**at most 10 per purchased Topic** — the formal set is the deliverable; the
candidate set may be larger. Ten or more genuinely distinct important intents
is a split signal, acted on at formal-set selection when the brand party
cannot pick its 10 without dropping intents it needs — not a candidate-stage
cap and not a pre-quote auto-split (after-sales-rules.md → *When to
split a Topic*); candidate Prompt counts carry no upper bound. Weight the counts rather than equalising
them — the weight follows the P1 rows. **For one market × one product line the bank may total 30–60 Prompts across the three layers, of which the core layer needs only 20–30** (Suda 2026-10-23; core = the non-branded Discovery Prompts that run every period, see representative-library.md → *Roles and Refresh*): go beyond 30 core only to cover a P1 row that would otherwise have no Prompt, and say which. The experimental and monitoring layers make up the rest. Candidate Topics below five remain
explicitly pending merge, Tag treatment, or evidence completion. **Before concluding a Topic is short, re-check attribution**: a Prompt filed under the wrong Topic is a common cause of one Topic falling under the floor while another quietly carries a Prompt that does not serve it. Move it to where its actual purchase decision belongs, then count again — that is a correction, not padding. Do not add a
Prompt to fill a visual gap, or turn the presales `<=60` discovery-stage limit
into a permanent after-sales library cap.

## Output

Unless the user requests another format, deliver:

- A customer-facing confirmation Base when the task involves scope confirmation, Topic approval, or Prompt wording and tier approval. Follow [client-facing-attribute-pool.md](references/client-facing-attribute-pool.md): 提示词库 is the table the brand party always reads, 业务范围 the facts they confirm, 属性池 / 主题 / 提示词矩阵 optional reading; in the Base the brand party edits cells directly; a document-format piece gives every table a `客户确认` column using the write-what-to-change convention.
- A machine-readable JSON monitoring set.
- An upload CSV. **For the online presales diagnosis upload, always export the nine-column template with `scripts/export_upload_csv.py`** (output-contract.md → *CSV*); the online page rejects any other shape (Suda 2026-10-29 — a hand-written five-column file could not be uploaded). The five columns `query,question_zh,topic,region,prompt_type`, plus `tags` and/or `cadence`, are only for a monitoring pipeline that asks for them; add no other columns.
- A cadence/schedule file.
- An input/evidence diff listing why each Topic or Prompt was added, changed, merged, or retained.
- In that same internal diff, a compact market-coverage section: reviewed slices, local evidence, retained/omitted intent decisions and reasons. Its filled situations are the client Base's 提示词矩阵 table, linked to 属性池; do not build a second matrix.
- A short validation summary that opens with the validator's readiness line (Not ready / Usable / Ready, see the verdict note after output-contract gate 37), plus known incompatibilities when an older presales validator enforces fixed quotas. List the unused buyer quotes the validator reports, each with its decision.

For a single-product update such as Bbrand N1, keep the new product line isolated from unrelated product Topics. Reuse frozen Case boundaries, but do not carry unrelated competitors into the new Topic.

## Maintaining this skill

After any change to a rule, run `python3 -I scripts/check_skill_terms.py` (it scans this skill, `geo-monitoring` and `shared/canonical-intent-mapping.md` for retired wording) together with the validator tests and `evals/verify_workflow.py`; a rule change is done only when the scan reports zero hits and both pass. Add the retired phrase to the scanner's list in the same change that retires it.
